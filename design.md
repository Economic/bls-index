# Plan: build and publish a current BLS series catalog

## Purpose and boundary

This is a **standalone `bls_index` project**. Build a reproducible, current, downloadable index of BLS series IDs and searchable titles from the official flat files at `https://download.bls.gov/pub/time.series/`. Do not implement or change `epidatatools` here. A future `epidatatools::find_bls()` may download the published file into a user cache and search it locally; the index must therefore have a documented, stable file format and discovery mechanism. No hosted query API, browser UI, SQLite-over-HTTP, or DuckDB remote range-read requirement for v1.

“Current” means **present in the latest successfully ingested BLS `.series` files**, not necessarily still receiving observations. Frozen but still published series belong in the catalog; series removed from BLS files do not. Record source freshness explicitly, and never describe a failed or outdated build as a fresh snapshot. The research note `research/2026-08-11-existing-bls-series-catalogs.md` is the starting inventory, not a substitute for validating current BLS files.

## Deliverable and contract

- Publish one canonical, compressed `bls_index.parquet` per successful refresh (served at an immutable `bls_index-<checksum>.parquet` URL). Start with a flat search schema: `program`, `series_id`, `series_title`, `title_source` (`native`/`synthesized`), `seasonal` (SA/NSA/unknown), `begin_year`, `end_year`, and `end_period`. v1 has no `status` column; clients judge liveness from the year and period fields. Include `survey_name` and `begin_period` if verified and useful; nullable values must stay nullable rather than be guessed. Specify types, normalization, and schema version in documentation. Keep IDs as strings, trim BLS padding, and preserve the original BLS title when supplied. Do not treat BLS survey/program codes as interchangeable without an explicit mapping.
- Maintain a repository-root `data-dict.yaml` (the documented data-dict naming convention) with `name: bls_index` and a Parquet source pointing to the local `bls_index.parquet`. Define column meanings and types, nullable fields, allowed categorical values, and machine-checkable constraints (including required IDs/titles and uniqueness where verified). Pin the `data-dict` CLI version; run `validate-spec`, `validate-meta`, and `validate-data` on every publication candidate in CI. The dictionary's `$version` identifies the data-dict specification, separately from this catalog's own schema version. Measure full-data validation cost and keep nonexpressible BLS-specific checks in the build tests. Keep the authoritative dictionary in the repository; if also publishing it beside the artifact, arrange a stable source path (or generate a publication copy pointing to the immutable artifact) and validate that copy. Runtime clients do not need the CLI.
- Publish a small `latest.json` with two groups of fields. **Artifact fields** (schema version, artifact URL, SHA-256, byte size, build timestamp in UTC, per-program source timestamps or identifiers, and coverage counts listing the included programs) change only after a new artifact is uploaded and validated. **Check fields** (`last_checked_at`, `last_check_result`, per-program check times or errors, and a `stale_after` timestamp) are rewritten on every run, including runs with unchanged inputs and failed runs, without moving the artifact pointer. A stable manifest URL points to a **content-addressed** Parquet filename; the catalog file at that filename never changes.
- Keep only the current artifact plus a short-lived predecessor during cache propagation or rollback. Delete obsolete artifacts after the grace window; this is not a historical archive. Cleanup re-reads `latest.json` at the time it runs and never deletes the artifact it references or that artifact's predecessor. The manifest's artifact fields remain pointed at the last valid catalog if a build fails.
- Provide a documented build command, pinned dependencies, fixtures, automated tests, validation report, and an operational runbook (credentials, manual rebuild, rollback, alerting, and expected costs). Never commit R2 credentials or raw BLS bulk files.

The research scoped 54 programs and about 9.48 million series: 30 programs with native titles in full; 24 without native titles requiring title synthesis; exclude `nw` and the ten case-characteristics tier-3 programs initially. v1 covers the 30 native-title programs plus the three live untitled programs (`sm`, `jt`, and `pr`); the other 21 untitled programs follow in later releases. Re-check the directory list and counts at build time. The estimate of ~50 MB for a compact Parquet file is **not a measured v1 deliverable**: measure final bytes, download time, and local query performance before settling the schema and refresh cadence.

## Work sequence

### 1. Establish the reproducible ingest

- Choose a maintainable build language and pin a runtime plus dependencies; keep the pipeline independent of the `epidatatools` package. Document one local build invocation used unchanged in CI.
- Inventory in-scope BLS `.series` files and the lookup files needed for untitled programs. Fetch via HTTPS with a descriptive, contactable User-Agent, bounded concurrency, retries with backoff, and sensible timeouts. Every run rebuilds all in-scope programs, frozen ones included, from current BLS files. Record `ETag`, `Last-Modified`, size, and SHA-256 for every input file. Cache raw files between runs outside the repository (for example, in the GitHub Actions cache) and send conditional requests; use a cached file only when BLS confirms it is unchanged, and otherwise download it again. Do not assume byte-range support or compression on BLS downloads. Download to temporary files and verify full responses before parsing. After a program's files are downloaded, recheck each file's `Last-Modified`, `ETag`, and size against the recorded values (or, where headers are missing or unreliable, re-download the small lookup files and compare hashes). If any input changed, re-download the program's files up to a fixed number of retries, then fail that program.
- Normalize per-program schemas explicitly; fail on unexpected layouts instead of silently shifting fields. Cover anomalies recorded in the research (`cc` concatenated header/row; extra trailing fields in `eb`, `ec`, `ee`, `gp`, `hs`, `pd`, `sa`, `sh`, `si`; `hs` shifted year columns; `kv` without year fields). Trim padded IDs and validate that IDs and decoded dimensions are plausible. Keep provenance for every row.
- Build titles in four program-family milestones, each reviewed and accepted before the next begins:
  1. The 30 native-title programs (`ap`, `bd`, `ce`, `ci`, `cm`, `cu`, `cw`, `cx`, `ei`, `ep`, `fm`, `ip`, `is`, `kv`, `la`, `le`, `ln`, `lu`, `mp`, `nb`, `nd`, `oe`, `or`, `pc`, `su`, `tu`, `wd`, `wm`, `wp`, and `ws`), plus title templates for the live untitled programs `sm`, `jt`, and `pr`. This milestone is published as v1.
  2. Frozen twins of titled programs: `ee`, `sa`, `mu`, `mw`, `pd`, `cc`, `ec`, `nc`, `eb`, and `jl`.
  3. Injuries and illnesses: `ii`, `sh`, `hs`, and `si`.
  4. Standalone frozen programs: `ml`, `gp`, `in`, `gg`, `bp`, `li`, and `bg`.

  Label synthesized titles. For each milestone, check that every series matches exactly one row in each lookup table, no labels are missing, synthesized title counts equal `.series` row counts, and titles are unique within each program; test each program with representative known series. A release's coverage counts list the programs it includes; do not describe any release as covering all 54 programs until milestone 4 passes.

### 2. Define and test the catalog semantics

- Set documented rules for seasonal adjustment and missing metadata. Preserve frozen, still-listed series. No first-seen/last-seen state store is required for v1; disappearance from a current BLS source removes an ID in the next valid snapshot.
- Enforce uniqueness of `series_id` (or document and test any genuine cross-program collision), nonempty titles, valid program assignments, sensible years, and predictable nulls. Reject unexpected row-count drops, program omissions, title-join explosions, malformed text, or missing required columns; thresholds should be explicit and require investigation rather than masking genuine BLS changes.
- Compare representative IDs against BLS files and, where feasible, the BLS data API: common unemployment/CPS, CES, CPI, JOLTS, and OEWS cases; include frozen and deleted-ID cases. Verify that the published artifact and the manifest's artifact fields are left untouched when inputs or validation fail, while the check fields record the failure.
- Benchmark search on a downloaded local file for realistic queries, including `unemployment` and an OEWS occupation, with a survey restriction and seasonality filter. Document that free-text search semantics and relevance ranking belong to consuming clients unless a common search specification is deliberately added later. Avoid claiming subsecond searches or a particular artifact size until measured.

### 3. Automate builds without operating a server

- Use a **scheduled GitHub Actions workflow** in a public `bls_index` repository on a standard Linux runner, plus manual dispatch. Serialize runs with a concurrency group (`group: bls-index-publish`, `cancel-in-progress: false`) so a second run waits rather than overlapping or interrupting an upload. Manual rebuilds go through workflow dispatch, not local machines, so the lock covers them. Test that actual memory, disk, runtime, BLS network access, and dependency setup fit runner limits; the research's few-minute full rebuild is an estimate. If public hosting is unsuitable, measure private-repo minute usage before considering a self-hosted runner. Cloudflare Workers Cron is not the bulk build environment.
- Build a candidate, run the pinned `data-dict` CLI's `validate-spec`, `validate-meta`, and `validate-data` plus BLS-specific schema, coverage, and provenance checks; calculate SHA-256 and sizes, and produce a machine-readable validation summary. If inputs have not changed, skip publishing a new artifact, but still update the manifest's check fields. Upload with a narrowly scoped R2 write token from CI secrets. Read back and verify the candidate object, then atomically switch `latest.json` last. On any failure, alert maintainers, record the failure in the manifest's check fields, and keep the artifact fields and artifact unchanged. Support a manual rollback by repointing the manifest during the grace period.
- Report build age and source ages; add a failure/staleness notification so a quietly stopped daily job is visible. Specify how to handle upstream outages. Frozen datasets are rechecked on every run like live ones; avoid permanent blind trust in a one-time download.

### 4. Serve safely and cheaply

- Store the Parquet and manifest in an R2 **Standard** bucket exposed through a dedicated Cloudflare custom domain; turn off the public `r2.dev` URL so security/cache rules cannot be bypassed through it. No API keys for read access; downloads must work from non-browser tools such as R and `curl` without JavaScript challenges.
- Configure a narrow Cache Rule for the immutable `.parquet` paths (not all site traffic), with a long TTL; configure a short TTL for `latest.json` so publication propagates promptly. Check `Cache-Control`, `ETag`, `Content-Length`, and actual cache hit/miss behavior after launch. `.parquet` is not cached by Cloudflare by default. Avoid cookies or arbitrary query strings in published URLs that fragment the cache.
- Add a conservative per-IP, path-scoped WAF rate-limit **block** rule only after measuring legitimate traffic; leave room for shared institutional IPs. Do not use CAPTCHA/Managed Challenge for the machine-readable download. Add usage and budget alerts, understanding that alerts are not hard cost caps. Document that caching and rate limiting mitigate abuse but do not guarantee a maximum bill. Revisit protections using measured R2 Class B reads and edge hit rates.
- Verify cold download, repeated download, checksum validation, manifest refresh, and old-file cleanup from an external machine. Test both fresh and cached requests and a failure/rollback path. Keep the catalog within the chosen CDN's cacheable size limit or revise serving strategy.

## Interface reserved for future `epidatatools` integration

Publish `data-dict.yaml`, schema and manifest examples, a checksum verification example, a small fixture, and the stable manifest URL. The future client can check the manifest at a documented interval, fetch a new file once to `tools::R_user_dir("epidatatools", "cache")`, verify the checksum and supported catalog schema version, check essential columns/types, swap the cache atomically, and search locally/offline afterward. It does not need the `data-dict` CLI or a full-row validation scan at runtime. Expose catalog source and age to callers, and treat the catalog as stale after the manifest's `stale_after` time. This integration, its user-consent/download UX, API compatibility, CRAN checks, and relevance ranking are **out of scope for this repository**; do not make the index build depend on `epidatatools`.

## Done when

1. A clean checkout can reproduce the build and tests locally and in CI without private local data.
2. v1 ingests the 33 milestone-1 programs (the 30 native-title programs plus `sm`, `jt`, and `pr`), with correctly labeled native/synthesized titles, documented exclusions, and automated anomaly/uniqueness/coverage checks. The remaining 21 untitled programs are scheduled as milestones 2 through 4. For v1, a pinned `data-dict` validator passes specification, metadata, and full-data checks on the candidate Parquet; real final size, validation cost, and search benchmarks are recorded.
3. A scheduled refresh publishes only validated changes, keeps the last valid catalog on failure, updates the manifest's check fields on every run, exposes truthful source/build timestamps, serializes overlapping runs, and alerts on prolonged staleness.
4. The HTTPS manifest and Parquet download work without credentials or browser verification; checksum, caching, rollback, cleanup, and a representative client download have been tested.
5. A public schema, freshness policy, operational runbook, and narrowly scoped Cloudflare protections exist; no `epidatatools` source changes are required to consider this project delivered.

## Decisions
<!-- Review findings and how each was resolved. -->

- **Separate artifact fields from check fields in `latest.json`** (roborev job 3, finding 2). Because the manifest changes only when a new artifact is published, a no-change run leaves an old build timestamp that looks stale. After failed runs, the last "passed" outcome still looks healthy, and a client cannot tell either case from a stopped job. Artifact fields (`artifact_url`, `sha256`, `bytes`, `built_at`, and per-program source identifiers) change only when a new artifact is published. Check fields (`last_checked_at`, `last_check_result`, and per-program check times or errors) are rewritten on every run, including no-change and failed runs, without moving the artifact pointer. The manifest also carries a `stale_after` timestamp so clients can detect staleness without knowing the refresh cadence. Keep both groups in one file so clients make a single request.
- **Serialize builds and clean up from the current manifest** (roborev job 3, finding 3). Scheduled and manual runs can overlap. An older run that finishes last would repoint `latest.json` to older data, and its cleanup could delete the newer artifact the manifest now references, breaking every download. The workflow uses a GitHub Actions concurrency group (`group: bls-index-publish`, `cancel-in-progress: false`), so a second run waits rather than overlapping or interrupting an upload. Manual rebuilds go through workflow dispatch, not local machines, so the lock covers them. Cleanup re-reads `latest.json` and never deletes the artifact it references or its predecessor. A conditional manifest write that rejects older source versions was not adopted: "older" is hard to define across 54 programs, and serialization plus manifest-based cleanup covers the realistic cases.
- **Recheck a program's inputs after downloading them** (roborev job 3, finding 4). Untitled programs build titles by joining a `.series` file with lookup files fetched at different moments. If BLS updates one mid-build, the join can mix revisions and still pass cardinality and missing-label checks, especially when a code keeps its value but gets a new label. After a program's files are downloaded, re-request each file's `Last-Modified`, `ETag`, and size and compare them with the values recorded at download. Where BLS headers are missing or unreliable, re-download the small lookup files and compare SHA-256 hashes. If any input changed, re-download the program's files, up to a fixed number of retries, then fail that program rather than publish mixed titles.
- **Drop `status` from the v1 schema** (roborev job 3, finding 5). The review asked for rules that classify each series as live, frozen, or unknown. `end_year` alone is unreliable: annual programs publish with a lag, discontinued programs remain listed, `kv` has no year fields, and `hs` has shifted year columns. A dependable rule would need a hand-maintained table of each program's status, frequency, and lag. Instead, v1 publishes `begin_year`, `end_year`, and the ending period, and leaves liveness judgments to clients. Adding `status` in a later schema version is backward compatible; changing the meaning of a published column is not.
- **Build titles in program-family milestones** (roborev job 3, finding 6). Grouping all 24 untitled programs into one step leaves no checkpoint where a program's joins are reviewed before the next begins. Work proceeds in four milestones, and milestone 1 is published on its own as v1: (1) the 30 native-title programs plus the three live untitled programs, `sm`, `jt`, and `pr`; (2) frozen twins of titled programs: `ee`, `sa`, `mu`, `mw`, `pd`, `cc`, `ec`, `nc`, `eb`, and `jl`; (3) injuries and illnesses: `ii`, `sh`, `hs`, and `si`; (4) standalone frozen programs: `ml`, `gp`, `in`, `gg`, `bp`, `li`, and `bg`. Each milestone passes its own acceptance checks: every series matches exactly one row in each lookup table, no labels are missing, synthesized title counts equal `.series` row counts, titles are unique within each program, and representative series match BLS descriptions. Milestones 2 through 4 are added in later releases. Adding programs adds rows, not columns, so it does not change the catalog schema version. Each release's manifest coverage counts list the programs it includes, and no release is described as covering all 54 programs until milestone 4 passes. Frozen programs are rebuilt from current BLS files on every run rather than synthesized once and cached. Each run sends conditional requests using the stored `ETag` and `Last-Modified` for every input file. Raw files are cached between runs outside the repository (for example, in the GitHub Actions cache), and a cached file is used only when BLS confirms it is unchanged. Otherwise, the file is downloaded again. The index should contain exactly the series available from BLS today: what is in the current files can be retrieved through the BLS API, and what BLS has removed cannot, so titles cached from an old build could only add series that are no longer useful to look up.
