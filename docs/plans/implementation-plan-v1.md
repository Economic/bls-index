# Implementation plan: downloadable BLS series catalog (v1 draft)

This is a first implementation draft for the standalone `bls_index` repository. The [current design](../../design.md) is the contract; the [research inventory](../../research/2026-08-11-existing-bls-series-catalogs.md) supplies starting counts, sample anomalies, and preliminary performance measurements, not a fixed source snapshot. Where the research proposes conditional downloads, caching frozen inputs, live/frozen status, a browser search index, or a 54-program initial release, follow the newer design instead. No `epidatatools` changes, hosted search API, or browser UI are part of v1.

## Scope and sequence

The **first publication is exactly 33 programs**, in two implementation checkpoints:

1. Native BLS titles: `ap`, `bd`, `ce`, `ci`, `cm`, `cu`, `cw`, `cx`, `ei`, `ep`, `fm`, `ip`, `is`, `kv`, `la`, `le`, `ln`, `lu`, `mp`, `nb`, `nd`, `oe`, `or`, `pc`, `su`, `tu`, `wd`, `wm`, `wp`, `ws` (30). Preserve source title text; duplicate titles are valid.
2. Synthesized titles: `sm`, `jt`, `pr` (3). Complete and review each program's lookup joins and title template before first publication.

Keep a fixed canonical initial list in code and tests. Do not infer published scope from the BLS directory or later milestone lists. The research's ~8.29 million native-title rows and ~25,269 rows in the three untitled programs are historical reference measurements; recount current sources. `nw` and the ten case-characteristics programs are excluded. Checkpoints 3–5 of the design (the remaining 21 additions) are **future separate releases**, not v1 tasks or daily targets: frozen twins `ee`, `sa`, `mu`, `mw`, `pd`, `cc`, `ec`, `nc`, `eb`, `jl`; injuries `ii`, `sh`, `hs`, `si`; standalone frozen `ml`, `gp`, `in`, `gg`, `bp`, `li`, `bg`. Each later checkpoint needs its own tested implementation and explicitly approved scope release. Frozen but still-listed rows in included programs remain in v1; no series-level `status` or lifecycle guesses.

## Phase 0 — Establish the build and controlled integration harness

- Select a maintainable standalone build language/runtime, pin exact versions of dependencies and the `data-dict` CLI **after** checking actual CLI commands/constraint support and clean-runner installation; define one reproducible local build/test command reused by CI. Lay out a small build package, fixtures, fixed initial scope and documentation without storing bulk inputs or credentials in Git. Do not copy the research note's R/Arrow/DuckDB versions as unverified implementation pins.
- Build the greenfield integration/fault-injection harness **before** implementing manifest transitions or publication. Provide a controlled HTTP source serving fixture `.series` and lookup bodies with configurable 200/404/403, timeout, truncation, schema drift, and content changes between reads; an object-store adapter exercised against a local S3-compatible service or isolated R2-equivalent with upload/read-back, conditional manifest writes, read errors and corruption injection; an injected UTC clock; an independent fake notifier that can fail; and a recorded ordered event log of downloads, validation, object operations, notifications and manifest writes. Use these interfaces in the production workflow, not a test-only reimplementation. Keep local/public namespaces and credentials separate. Start with a tiny two-program fixture for fast state-machine tests and add an all-33 fixture for the first-publication gate. Verify harness tests themselves: clock-controlled exact boundaries, HTTP response/fault replay, object corruption and denied reads, notifier capture/failure, and assertion that immutable read-back verification precedes the final manifest switch; CI runs these without live BLS or public credentials.
- Probe real BLS HTTPS from the intended Linux Actions runner with a descriptive contactable User-Agent, timeouts, bounded concurrency and retry/backoff. Inventory each initial `.series` and the `sm`/`jt`/`pr` lookups; record URL, response metadata, bytes, SHA-256, observed schema, counts and lookup dependencies. Never use `HEAD`, ETag or modified time to skip daily downloads. Download into temporary storage, detect incomplete responses, and recheck **every** input including `.series` for mid-build changes (validators only if their reliability is established; otherwise re-download and compare body SHA-256); retry the entire program input set to a bounded limit. A later staging deployment check must additionally verify actual R2 credentials/conditional writes/read-back, GitHub serialization and notifier delivery; harness success alone is not a deployment check.

**Gate 0:** Controlled two-program harness and its fault/ordering self-tests pass in CI; representative large (`oe`) and small real inputs can be fetched on a clean runner; recording the runner's available resources and quotas precedes architecture selection. The **full 33-program** resource, validation and query benchmark follows completion of all 33 parsers in Gate 1, not this phase.

## Phase 1 — Reproducible per-program builders and catalog contract

- Define versioned canonical Parquet schema and documentation: required string `program`, trimmed string `series_id`, nonempty string `series_title`, `title_source` (`native`/`synthesized`), `seasonal` (SA/NSA/unknown), nullable `begin_year`, `end_year`, `end_period`; include nullable `survey_name` and `begin_period` only after verifying their meaning. Document field types, null rules, program-versus-survey code mapping, normalization, and stable file discovery. Preserve BLS-provided title text rather than constructing a replacement. Years/periods are source metadata, **not** liveness. A compressed `bls_index.parquet` is the sole canonical combined search file, served at an immutable `bls_index-<sha256>.parquet` URL.
- Implement explicit schema adapters for the 30 native-title programs, strict tab/field parsing, padded-ID trimming, encoding and year/period checks, and a compact per-program Parquet output carrying input checksums and actual source-built time. Cover `kv`'s missing year fields without invented dates. Recognize historical anomalous layouts where applicable; unexpected columns, misplaced years, malformed text, empty input, 404, or changed/incomplete input fail **that program** with a diagnostic. Add fixtures for the documented `cc` concatenation, trailing fields in `eb`, `ec`, `ee`, `gp`, `hs`, `pd`, `sa`, `sh`, `si`, and shifted `hs` years for future checkpoints, without silently expanding v1 scope.
- Validate each native program independently: required fields and valid program assignment, plausible IDs and years, stable row-to-ID mapping, reasonable count-change investigation threshold, nonempty titles, and no unexpected join/parse loss. Check verified ID uniqueness across the combined scope (document and test any real cross-program collisions); never require unique titles. Compare representative BLS file rows, including CES, CPI, CPS/unemployment, OEWS and frozen still-listed IDs, and consult the BLS data API where feasible without making the API a build dependency.
- After the native checkpoint passes, implement `sm`, `jt`, `pr` lookup adapters and reviewed title templates. Require exactly one lookup row for each decoded dimension, no missing labels, one output per `.series` row, and representative titles checked against BLS descriptions. Include a fixture that detects duplicate join keys/row multiplication. Store `title_source` per row and verify it matches the builder used.
- Create repository-root `data-dict.yaml` (`name: bls_index`, local Parquet source `bls_index.parquet`) with column definitions/types/nullability, categorical values and machine-checkable ID/title/verified-uniqueness constraints. Its `$version` denotes the dictionary specification, not the catalog schema version. Run pinned `validate-spec`, `validate-meta`, and `validate-data` against **every combined candidate** in CI; put BLS-specific assertions that the dictionary cannot express in build tests. If a dictionary is also served beside the artifact, validate a publication copy whose source resolves to the immutable artifact, while preserving the root dictionary as authoritative.

- **Only after all 33 parsers/templates and combined validation work**, run a representative full-33 dry build on the intended runner (no public writes). Measure peak RAM/disk, download bytes/time, parse and Parquet bytes/time, immutable-object read-back/checksum time, full-data dictionary validation time, daily Actions minutes versus applicable caps, R2 storage/read estimates, and downloaded local query times for `unemployment` and an OEWS occupation with program and seasonality filters. Record rows per program and actual inputs; compare the research's older 30/54-program figures only as historical baselines. Choose bounded concurrency or streaming after observing runner limits; set usage monitoring/alerts, and rerun the benchmark after architecture changes. Record the chosen retry limit and count-drop investigation thresholds from measured normal variance and documented failure cases, not the old counts.

**Gate 1:** The 30 native builders and then all three synthesized builders pass fixtures and sample source comparisons; all 33 independently validate from fresh inputs; a complete candidate passes combined invariants and all three pinned dictionary commands. The full-33 runner benchmark and query results are recorded and feasible within observed caps (or architecture is revised and remeasured). Publish nothing yet; investigate discrepancies instead of freezing historical counts as thresholds.

## Phase 2 — Manifest, durable files, and safe daily publication

- Implement the common manifest write outcome protocol for first create, daily artifact/status mutation, scope release, rollback, and recovery. Maintain one authoritative durable operation journal/index at a configured private location, not publicly readable and excluded from artifact cleanup. Its conditionally updated entries contain a unique `manifest_write_id`, full intended manifest content, exact expected prior version (including expected absence), and lifecycle state: `prepared` (no request dispatched), `submitting` (request may have reached storage), then terminal `resolved_committed` or `resolved_noncommitted`. Persist and confirm `prepared` via create-if-absent/CAS, then durably CAS to `submitting` immediately before dispatch; do not dispatch unless both phases are confirmed durable. If the journal update is uncertain, reconcile it authoritatively and do not submit unless the required phase is confirmed durable. A crashed `prepared` record proves no request was sent and may resolve non-committed after confirming the prior run ended. A crashed `submitting` record must be reconciled; old-state read proves non-commit only when tested store semantics exclude delayed/in-flight requests. Include the write identity in the manifest. Classify responses as committed, non-committed only when storage guarantees no commit (for example, a confirmed conditional rejection), or unknown. Reconcile a rejected/unknown write through an uncached authoritative manifest read: exact intended identity and full content proves commit; exact expected prior version or confirmed absence proves non-commit only when the tested store semantics establish that result (do not infer non-commit from an old-state read without verified semantics). A different version, inconclusive read, or unavailable/non-authoritative read proves neither outcome.

After determining the outcome, durably CAS the journal entry to its terminal resolved state before any next manifest mutation or cleanup; reconcile ambiguous journal responses, and stop if terminal durability remains unknown. Never reuse an ID or replay a terminal entry; retain terminal markers independently of publication-object cleanup. Every later serialized daily, release, rollback, or cleanup run must read the authoritative journal and resolve all nonterminal `prepared` or `submitting` entries in order before downloads or mutations. For a pre-submission crash, once the serialized prior process has ended, a `prepared` record proves dispatch did not occur because dispatch is forbidden before durable transition to `submitting`; durably mark it `resolved_noncommitted` without relying on an old-state manifest read. For a post-commit/pre-resolution crash, a `submitting` record must match exact intended identity and full content before persisting `resolved_committed`; if the old manifest remains, prove non-commit only under tested semantics that exclude a delayed/in-flight request. Any unresolved outcome or unconfirmed journal state independently alerts and stops all mutations, downloads and cleanup; do not retry the manifest write, roll back, write status, or claim unchanged/absent. After a durably resolved non-commit, rebuild from latest authoritative state and recheck preconditions/approval before a new write. Follow-up status writes are separate identified operations governed by the same protocol. Gate production on staging evidence that the private journal is durable/discoverable across runs and its conditional updates/read semantics are adequate; do not assume unverified object-store consistency.
- Define and test a documented `latest.json` schema before wiring storage. `current` includes catalog schema version, immutable URL/SHA-256/byte size/build time, exact `required_programs` and coverage counts, and each included program's immutable R2 URL/SHA-256, source input checksums and actual source-built time. Track `scope_revision`, per-program last attempt time/outcome/error and last-good URL/SHA-256/time, whether `current` used a new or last-good file, `last_attempt_at`, `manifest_updated_at`, `last_complete_successful_source_verification_at`, and status. Store the complete prior artifact record as `previous`, including its exact scope and actual complete-verification time, with a documented grace expiry. Document absent `previous` on first publication and avoid claiming that attempt records equal published coverage.
- Implement one authoritative manifest reader for daily, release, rollback and cleanup: distinguish a **confirmed absence** (successful authoritative metadata lookup returning an explicit not-found for the configured key; unrelated old immutable objects do not imply a manifest) from present-and-supported; timeout, transport failure, 403, malformed JSON, corrupt/incomplete body, invalid fields and unsupported schema are **errors**, never absence. On ambiguous or erroneous reads, fail closed before downloading, promoting, rolling back or deleting; log and independently alert, retaining the last public pointer. Only confirmed absence may enter the fixed-33 first-publication path or grace-delayed cleanup of unreferenced first-attempt uploads; release, rollback, and cleanup of published references require a valid existing manifest. Test read-after-write and conditional compare-and-swap behavior on the selected object store, including concurrent/stale state; if the store cannot provide an atomic/conditional manifest replacement with the required observed semantics, choose and verify an equivalent serialized atomic publication mechanism before enabling publication. Do not claim an unverified R2 API guarantees these semantics.
- Build a state machine with separate daily and first-publication paths. Every **started** scheduled or manual daily run reads the published manifest's `required_programs`, downloads and rebuilds **every and only** listed program (before first manifest, the fixed 33); no conditional skip, frozen-file exemption, milestone promotion, or automatic removal after a missing source. Pending GitHub Actions runs canceled before execution do not count as attempts and do not change attempt records. Validate programs independently; upload successful compact files to immutable content-addressed R2 keys and read back/checksum-verify them. R2, not transient Actions artifacts, holds last-good copies and public files.
- For the **first** run, require fresh, validated files for all 33 from that **same run**, plus a passing combined candidate and dictionary validation. Define publication and discoverability of the catalog by a successful final `latest.json` manifest pointer, not by the immutable combined-object upload. A failure before the first manifest write, or a confirmed non-commit reconciled to manifest absence, leaves no published/discoverable catalog, regardless of old exploratory files; immutable uploads can still be publicly retrievable by known URL as unreferenced orphans. For an unknown first-write outcome, reconcile the intended manifest identity and full content before claiming whether the catalog is published. Record started failures and independently alert. Upload/read-back-verify immutable objects before writing the first manifest last.
- After first publication, select fresh files for successful current-scope programs and checksum-verified R2 last-good files for failed ones; validate the assembled full-scope candidate, including dictionary checks. If any required valid copy is unavailable, or aggregate assembly/validation/upload fails before a manifest switch is attempted, retain `current` and scope; update attempt/error/status fields only through a separately identified and reconciled manifest mutation, and alert. For a switch with a rejected or unknown response, reconcile before claiming the current pointer or attempting another mutation. A valid mixed candidate may switch `current` while clearly marked degraded (or stale). On each valid switch upload and read-back-verify all immutable data objects first, then atomically write `latest.json` with unchanged scope, complete prior `current` as `previous` and new grace expiry. Keep per-program last-good references aligned with successful new builds; fallback does not advance the program's source-built time.
- Update the complete-source-verification timestamp **only** if every published required program was freshly downloaded, parsed, and independently validated in the run; a successful complete daily publication records that timestamp with the corresponding artifact. Fresh requires such a complete no-fallback publication within 48 hours. Stale takes precedence if complete verification is older than 48 hours; clients also deem an over-48-hour `manifest_updated_at` stale. Otherwise degraded covers any latest current-scope failure, fallback, failed aggregate publication, or rollback awaiting complete rebuild; a recent partial check cannot make an old artifact fresh. Failed manifest writes require an independent workflow/monitoring alert because the manifest cannot report its own failure.

**Gate 2:** Controlled fault-injection tests prove that a pre-write first-attempt failure or confirmed non-commit reconciled to absence creates no discoverable published catalog, even if a verified immutable upload remains addressable by its URL; an unknown first-write outcome is reconciled before any publication claim. Current-scope failures use only valid last-good files; missing last-good or aggregate failure before a switch leaves the pointer untouched; a mixed publication is not fresh; exact scope and real verification times persist; commit-then-drop, confirmed rejection, unavailable reconciliation, and failed manifest writes alert and follow the common protocol; pending cancellation does not create an attempt. Only isolated staging writes are allowed here; the first **production** switch requires the separate launch gate after Phases 3–4, plus an all-33 same-run pass.

## Phase 3 — Explicit scope releases, rollback, and cleanup

- Build a distinct manual GitHub Actions scope-release mode, unavailable before first publication. Validate `target_programs` **before downloading**: nonempty, unique, canonical, implemented and tested. Show exact additions/removals against published scope and require explicit operator confirmation of that exact change, including contraction, bound to `(scope_revision, exact canonical required_programs)`. Decide and document an approval mechanism; re-read/recheck the base fingerprint before downloads and immediately before the atomic switch. A daily artifact/status write with unchanged fingerprint does not invalidate approval; a scope change does. Increment `scope_revision` only on a successful scope-changing release, never on daily writes. Reject stale approval without changing scope or downloading if detected before downloads.
- A confirmed release freshly builds and validates **all target programs in one run**, without fallback even for existing programs, validates the full target candidate and dictionary, uploads and read-back-verifies all immutable files, and atomically switches artifact plus exact scope. Advance verification for the resulting scope in that write, pin **every** target last-good file/checksum/actual source-built time to the release files, and discard out-of-target last-good records. A release validation or other pre-switch failure, or a confirmed non-commit reconciled to the prior manifest, keeps artifact and scope and never advances complete verification; report/independently alert it. For an unknown switch outcome, follow the common protocol and do not claim unchanged pointers/scope or write status before reconciliation. A failure limited to proposed-only programs does not alter published status; validation failure in an included current-scope program records/reports that failure and degrades the current catalog where writable unless already stale. No source 404 or empty file requests contraction.
- Serialize scheduled and manual daily rebuild, release, rollback, and cleanup in the GitHub Actions `bls-index-publish` concurrency group with `cancel-in-progress: false`. Operators must re-trigger a pending manual request displaced by another pending request. Implement rollback only to checksum-verified unexpired `previous` with **identical scope**: verify combined and all per-program files, atomically swap complete records, give displaced `current` a new grace expiry, restore each program's exact old file and actual source-built time as last-good, and restore the old scope's actual complete-verification time. Mark degraded pending a complete rebuild (stale if over 48 hours); checksum read-back or rollback does not constitute new source verification. Never select a displaced-version fallback until a new validated build for that program. Different-scope reversal requires a newly approved scope release. Document separately the post-expiry, independently verified same-scope recovery path; it cannot switch scope.
- Cleanup under the same lock re-reads the manifest just before deletion and protects every `current` object, unexpired `previous` object, and current-scope last-good file. Treat uploads left by a confirmed non-committed first manifest write reconciled to absence (including a combined object) as unreferenced orphans, not published artifacts; an unknown write outcome blocks cleanup until reconciled. Initial retries after confirmed absence must still build and validate all 33 afresh from the same run and must not use these uploads as initial last-good files. Only delete unreferenced objects, including orphans, after the documented grace period; expiry ends protection, not immediate deletion. If no manifest exists, confirm authoritative manifest-key absence before orphan cleanup; on an ambiguous read, crash, denied deletion or other cleanup failure, retain objects and alert rather than assume deletion succeeded or claim no publicly addressable uploads remain. Use a dry-run inventory before enabling deletion. Document credentials, independent alerts, stale/overdue monitoring, R2 costs, manual release, rollback, and upstream outage response in a runbook.

**Gate 3:** Tests reject invalid/duplicate/unsupported/unconfirmed targets before downloads; confirm exact additions and removals; reject an approval for scope A after A→B→A (revision increments twice), yet accept an unchanged fingerprint after a daily update. Pre-switch release failures and confirmed non-commits reconciled to the old version leave pointers, scope, last-good, and verification time unchanged except allowed, separately reconciled current-scope error/status fields; unknown outcomes must reconcile or stop without such claims. Success pins each target release file, discards out-of-target records, and a subsequent daily failure uses the release copy. Rollback restores timestamps and per-program fallback, refuses different/expired scope records, and remains degraded/stale until full rebuild. Cleanup never deletes protected references and only reclaims elapsed unreferenced objects.

## Phase 4 — CI, public delivery, and operational acceptance

- In CI, run deterministic parser/title fixtures, controlled integration/fault-injection tests, dictionary spec/meta/full-data checks for combined publication candidates, schema compatibility checks, and a reproducible end-to-end dry run without credentials. Configure scheduled and manual build workflows on standard Linux runners, pinned dependency setup, serialization, independent maintainer alerting, logs and a machine-readable validation report; do not commit raw BLS files or credentials. Until the launch gate, use only staging namespace/bucket and staging-scoped write credentials; production writes must be disabled in workflow configuration, and neither staging URLs nor exploratory objects may be mistaken for the public manifest. Verify credential denial outside assigned object prefix and ensure public read access needs no token. Verify external alert delivery independently of the manifest for initial, release, upload, and manifest-write failures, including notifier-failure escalation; a log entry alone is not an alert.
- Publish through an R2 **Standard** bucket on a dedicated Cloudflare custom domain; disable public `r2.dev`. Configure narrow long-lived cache rule for immutable `.parquet` paths and short TTL for `latest.json`; `.parquet` is not cached by default. Verify `Cache-Control`, `ETag`, `Content-Length`, hit/miss behavior, size against CDN cacheable limit, SHA-256, cold/repeated `curl` and R-style download without credentials or browser challenges, and manifest refresh after full/mixed build, release, and rollback. Apply a conservative per-IP path-scoped WAF **block** rule only after measuring legitimate traffic, allowing shared IPs and no CAPTCHA/Managed Challenge for machine downloads; monitor R2 Class B reads, edge cache hits, usage and budget (alerts are not hard cost caps).
- Publish schema/manifest examples, stable manifest URL, checksum verification example, dictionary, small fixture and operational runbook. The future client may verify schema/checksum then cache locally; its API, search ranking, and `epidatatools` implementation are out of scope. Run an external-machine end-to-end exercise including failure/rollback and grace-period cleanup, and record actual source age, full workflow cost, artifact bytes, local query timings, and alert delivery.

**Staging gate (not production launch):** Run real staging GitHub Actions jobs against the intended R2 API/custom-domain configuration using staging-scoped secrets and the common `bls-index-publish` group. Demonstrate serialization and pending-cancellation semantics, atomic/conditional manifest behavior, upload/read-back/checksum, independent alert receipt when a manifest write fails, recovery from a failed publication, scoped credential denial, and unauthenticated external cold/cached R-style and `curl` downloads plus manifest propagation after a switch and rollback. Simulate faults only in isolated staging; never inject them into production. Record checks, operator, date and evidence before requesting launch.

**Production-launch gate (separate approval):** Keep production publication disabled until Gates 0–3, all numbered acceptance checks below, staging gate, scoped production credentials, independent alert/overdue monitor with tested delivery, rollback/cleanup recovery runbook, and independent final review are signed off. Then authorize production writes in a separate operator-approved change, run the first public all-33 same-run build with no fallback, verify its immutable objects and dictionary before writing the public manifest last, and run external public-delivery/cache/checksum and alert smoke checks. Before authorization, no production write is permitted; after authorization, only a successful first public `latest.json` makes the catalog discoverable and published. If the first manifest write is confirmed not committed and authoritative reconciliation confirms absence, no public manifest points to a catalog, but immutable uploads may remain addressable by known URLs as orphans; if the outcome is unknown, reconcile before claiming publication state or cleaning up. Alert independently and use grace-delayed orphan cleanup; a later initial attempt still rebuilds all 33 afresh. Future checkpoint programs are not required for v1.

## Numbered acceptance checks (CI names are suggested stable test identifiers)

1. **`test_harness_faults_and_order`:** Controlled HTTP body/status/timeout/changed-response fixtures, local S3-compatible or isolated R2-equivalent object store, injected UTC clock, fake notifier, and ordered event record all operate through production adapters. Assert download/parse/validate → upload → read-back SHA-256 of every chosen per-program and combined object → conditional final manifest write; failed read-back never switches. Exercise the common write outcome protocol for initial, daily artifact/status, release, rollback, and recovery mutations, with unique identities, retained full intended contents, and create-if-absent/CAS. Inject commits followed by dropped responses; authoritative uncached reads must recognize exact intended content as committed. Inject a confirmed conditional rejection and prove no-commit before rebuilding from latest state; inject unavailable/inconclusive reconciliation and prove the run alerts, stops all mutations, and makes no unchanged/absent claim. Add three cross-run crash/recovery cases using the same production journal adapter: (a) crash with durable `prepared` before transitioning to `submitting`; after confirming the prior run ended, the successor durably resolves the definitely undispatched write as `resolved_noncommitted` and completes a later write; (b) commit manifest A, crash while its journal record is `submitting` before persisting resolution, then successor discovers A from the journal, verifies exact intended identity and full content, durably records `resolved_committed`, and only then proceeds with B; (c) durably resolve A, commit subsequent write B, and crash before resolving B; the successor discovers A's terminal marker, never compares A's old candidate to manifest B or replays A, reconciles and durably resolves B, and successfully proceeds with a new operation. Assert each final journal/manifest state, operation ordering, no duplicate submission of resolved IDs, and no permanent blockage after resolvable crashes. Also inject failure/ambiguity persisting a terminal resolution and prove no later download, manifest mutation, or cleanup occurs until journal state is authoritatively resolved; a `submitting` record whose non-commit cannot be proved must stop rather than infer it from an old-state read. CI runs without public credentials; staging checks verify real storage/alert behavior separately.
2. **`test_source_identity_and_retries`:** Every started daily run downloads/rebuilds precisely published `required_programs` (or fixed 33 before first manifest) even if HEAD/ETag suggests no change; release uses only approved target. Change the bytes of a `.series` file *after* its first download while lookup files stay constant: recheck detects mismatch, retries the entire program set and records final source SHA-256/URL/response data or fails at the bounded limit. Repeat with a changed lookup and a truncated response. Neither failed input nor source 404 changes scope.
3. **`test_parsers_titles_and_dictionary`:** 30 native-title builders before `sm`, `jt`, `pr`; `kv` null years, padded IDs, malformed layout and future anomaly fixtures, duplicate native titles allowed, lookup key duplication/missing label rejected, exactly one output per `.series` row, plausible years/IDs and verified global ID uniqueness. Check representative native/synthesized rows and still-listed frozen series against source and feasible BLS API samples. Run pinned `validate-spec`, `validate-meta`, `validate-data` for **every** combined candidate; verify dictionary `$version` and catalog schema version are distinct. `check_full33_runner_benchmark` executes only after all parsers and records actual runner resources, full-data validation cost, Actions usage and local search timings.
4. **`test_valid_series_disappearance_vs_failed_program`:** Fixture one contains two individually valid, complete `.series` snapshots for the **same included program**: an ID exists in snapshot 1 but is absent in snapshot 2, while all 33 programs pass in each run. The second current artifact drops that ID and remains eligible for fresh status; a valid disappearance is not fallback or automatic program removal. Fixture two makes the program's entire download 404/empty/invalid in run 2: retain its validated last-good file in a full-scope mixed daily candidate, mark degraded (or stale), and keep the program in scope; if last-good is missing/corrupt, keep the prior combined pointer. Also reject unexplained row-count drops for investigation under the documented threshold rather than assuming every large disappearance is valid.
5. **`test_manifest_read_fail_closed_and_initial_run`:** Confirmed manifest-key absence selects fixed 33; preexisting immutable objects cannot fill any initial program or satisfy same-run validation. Failure of an initial program or combined validation before a write leaves no published catalog and sends an independent alert. Inject a confirmed first-create rejection after checksum-verified combined upload and reconcile authoritative absence: the object may still be fetched by known URL as an unreferenced orphan, not a published catalog; a new attempt rebuilds all 33 afresh and never uses it as initial fallback. Separately commit the first manifest then drop its response: reconciliation that matches the unique intended identity and full content recognizes publication and prevents an unsafe initial retry. If reconciliation is unavailable/inconclusive, alert and stop; do not claim absence, retry, write status, or clean up. Timeout, 403, malformed/corrupt/incomplete or unsupported manifest and uncertain existence cannot select first publication or mutate scope/artifacts. Release/rollback and cleanup of published references require a valid present manifest; orphan cleanup after confirmed absence obeys the grace/lock rules.
6. **`test_freshness_at_48h_boundary`:** At exactly 48 hours since the published scope's last complete successful source verification, do not mark stale on that basis; at 48 hours plus one clock tick mark stale, ahead of degraded. Clients likewise mark an exactly 48-hour-old `manifest_updated_at` not overdue and a later one stale. A recent manifest update or successful subset cannot advance complete verification or erase degraded/fallback; full no-fallback publication may become fresh within the window. A confirmed non-commit reconciled to the prior manifest leaves its pointer unchanged; a commit-then-dropped-response is recognized by reconciliation, and an unresolved outcome alerts/stops without asserting which pointer is current. Clients detect overdue state only if the timestamp they read remains old. A pending canceled request does not create an attempt/status write; a started failure does.
7. **`test_release_approval_and_revision`:** Reject empty, duplicate, noncanonical, unknown, unsupported, unconfirmed and unintended-contraction targets **before downloads**; display and confirm exact additions/removals including contractions against `(scope_revision, exact canonical required_programs)`. Recheck fingerprint before downloads and immediately before switch. Unchanged fingerprint after daily status/artifact write is valid; a changed fingerprint aborts and demands reapproval. Approval based on A is invalid after successful A→B→A releases even though list returns to A, since revision increased twice. A source 404 never proposes removal.
8. **`test_release_outcomes_and_fallback`:** A release rebuilds **every** confirmed target in the same run without fallback, verifies combined candidate and immutable objects, then atomically publishes exact target/current/previous, increases revision only for changed scope, advances target-scope verification and pins all target last-good URL/checksum/actual source-built times; discard out-of-target records. Inject commit-then-drop on the scope switch and reconcile as committed; inject a confirmed conditional rejection and reconcile the prior state before any rebuilt attempt. Next daily failure uses the release-pinned file. Proposed-only validation failure alerts but preserves published status/pointer/scope/last-good/time; currently published program validation failure can degrade status only through a separately identified, safely reconciled write unless stale. Unknown switch outcome or unavailable reconciliation stops all mutation; never assert old pointers/scope or advance verification without reconciliation. 9. **`test_rollback_cleanup_and_recovery`:** Verify previous combined and every per-program checksum, exact same scope and unexpired grace before ordinary rollback; atomically restore prior artifact, actual per-program times and complete-verification time and pin restored files as last-good. ## Decision register and review strategy

- **Implementer choices already fixed by the design/evidence:** immutable content-addressed compact Parquet and manifest-last publication; repository-root dictionary and per-candidate full-data validation; fixed initial 33 with native builders preceding synthesis; all published-scope programs redownloaded every started daily run, regardless of frozen metadata or unchanged HTTP headers; last-good only after first publication and only for daily current scope; manual release for any expansion, reintroduction or contraction; same-scope verified rollback and lock-protected cleanup. The research's ~50 MB estimate, full-54-program timings, skipped frozen inputs, lifecycle/status column and browser SQLite proposal are not implementation decisions.
- **Implementer decisions to record with evidence:** choose a standalone language using current runner/toolchain support and parser/Parquet capability, then pin and smoke-test exact versions (including `data-dict`) on a clean runner; choose explicit schema/version, status/errors, key layout, local S3-compatible or isolated R2-equivalent test service and object-store adapter, validator policy (prefer SHA-256 redownload unless header trust is demonstrated), bounded retry policy, source-specific seasonality/nullable fields and representative series. Select count-drop investigation thresholds from fixture failures/current source distributions; a threshold flags investigation, never authorizes removal. Confirm dictionary-expressible constraints against the actual pinned CLI; implement remaining checks in code. Do not invent version pins, reliable BLS validators, atomic R2 semantics or source layouts without checks.
- **Measured/operator decisions with hard gates:** choose concurrency/streaming and practical limits only after the full-33 runner benchmark; establish manifest atomic/conditional writes, freshness propagation and grace duration with staging R2/CDN tests before enabling switches/cleanup; test selected approval mechanism and exact-fingerprint confirmation with operators, including contractions, before scope release; choose independent alert destination/escalation only after receipt/failure tests; set WAF thresholds only after real traffic measurement. If a gate cannot be demonstrated, leave production publication disabled and document blocker rather than relaxing the design.
- **Review cadence:** review parser/title fixtures and source mapping at native checkpoint, independently inspect each of `sm`/`jt`/`pr` joins, review manifest/status/scope state-machine tests before staging, then review staging operations, credentials, security, rollback and runbook. Obtain an **independent final implementation review** by someone other than the implementer against this matrix and the current design, record findings and resolutions, rerun relevant CI and staging checks after fixes, and require written sign-off at the separate launch gate. Reviews do not authorize an automatic scope change.
