# Plan: build and publish a current BLS series catalog

## Purpose and boundary

This is a **standalone `bls_index` project**. Build a reproducible, current, downloadable index of BLS series IDs and searchable titles from the official flat files at `https://download.bls.gov/pub/time.series/`. Do not implement or change `epidatatools` here. A future `epidatatools::find_bls()` may download the published file into a user cache and search it locally; the index must therefore have a documented, stable file format and discovery mechanism. No hosted query API, browser UI, SQLite-over-HTTP, or DuckDB remote range-read requirement for v1.

“Current” means **present in the latest successfully ingested BLS `.series` files**, not necessarily still receiving observations. Frozen but still-listed series belong in the catalog. The catalog's source-verification freshness is separate from series liveness: do not infer that a series is live or frozen from its year or period fields, and never describe a failed, mixed, or overdue build as a fresh complete snapshot. The research note `research/2026-08-11-existing-bls-series-catalogs.md` is the starting inventory, not a substitute for validating current BLS files.

## Deliverable and contract

- Publish one canonical, compressed `bls_index.parquet` per assembled publication, served at an immutable `bls_index-<sha256>.parquet` URL. Start with a flat search schema: `program`, `series_id`, `series_title`, `title_source` (`native`/`synthesized`), `seasonal` (SA/NSA/unknown), `begin_year`, `end_year`, and `end_period`. v1 has no series-level liveness `status`; year and period fields describe source metadata only. Include `survey_name` and `begin_period` if verified and useful; nullable values must stay nullable rather than be guessed. Specify types, normalization, and schema version in documentation. Keep IDs as strings, trim BLS padding, and preserve the original BLS title when supplied. Do not treat BLS survey/program codes as interchangeable without an explicit mapping.
- Maintain a repository-root `data-dict.yaml` (the documented data-dict naming convention) with `name: bls_index` and a Parquet source pointing to the local `bls_index.parquet`. Define column meanings and types, nullable fields, allowed categorical values, and machine-checkable constraints (including required IDs/titles and verified ID uniqueness). Native titles are not required to be unique: distinct series may share a title. Do not use title uniqueness as a validation condition. Pin the `data-dict` CLI version; run `validate-spec`, `validate-meta`, and `validate-data` on every combined publication candidate in CI. The dictionary's `$version` identifies the data-dict specification, separately from this catalog's own schema version. Measure full-data validation cost and keep nonexpressible BLS-specific checks in the build tests. Keep the authoritative dictionary in the repository; if also publishing it beside the artifact, arrange a stable source path (or generate a publication copy pointing to the immutable artifact) and validate that copy. Runtime clients do not need the CLI.
- Publish a small `latest.json` manifest only with the first combined catalog, after every required program has succeeded in the same complete source-verification run and the combined candidate passes validation. Until that first publication, neither `latest.json` nor a public combined artifact exists; failed first attempts are recorded in the GitHub Actions run and trigger an independent maintainer alert. Once published, the manifest identifies `current` combined artifact (schema version, immutable URL, SHA-256, byte size, and artifact build time) and its exact per-program files (immutable R2 URL and SHA-256, plus source input checksums and source-built time). Its public `required_programs` list and coverage counts describe only programs actually present in `current`; they never describe a proposed or failed addition as included. Keep future milestone programs in a separate proposed/build scope until each addition passes per-program validation and a combined candidate containing it passes validation. A proposed addition is not included using a last-good file: if it fails validation or the candidate fails, leave the published artifact and `required_programs` unchanged. Promote the candidate and its program list together in the same atomic manifest write that switches `current`. The manifest also records each program's most recent attempt time, outcome, and error; its last-good file reference and time; and whether the current combined artifact used a new file or the last-good file, while keeping attempt records distinct from claims about published coverage. An attempt is a workflow run that actually starts execution; requests canceled while pending do not count as attempts and must not be reported as failed attempts or update per-program attempt/status records. Keep artifact identity separate from check/status fields, which are updated for each started run where the manifest is writable, including partial and failed runs.
- The manifest records `last_complete_successful_source_verification_at`: the time of the most recent run in which every program in the currently published `required_programs` list passed source download, parsing, and per-program validation. This timestamp does not advance on a partial run. Also record `last_attempt_at`, `manifest_updated_at`, and a clear overall status. Status precedence is `stale` first, then `degraded`, then `fresh`: stale means the last complete successful source verification is older than 48 hours, or clients find `manifest_updated_at` older than 48 hours; degraded means the latest run did not fully validate every currently published required program or the published catalog uses any last-good fallback; fresh is permitted only when the latest run fully validated every currently published required program, the published artifact uses those newly validated files, and the run is within 48 hours. Validation of a proposed addition does not advance complete-verification time or make the published catalog fresh until a combined candidate containing it passes and the candidate and updated program list are atomically published. Before the first public publication, no manifest exists to carry a status: failed attempts are recorded in the GitHub Actions run and trigger an independent maintainer alert. Publish the first catalog and manifest only after every required program succeeds in the same run and the combined candidate passes validation; per-program last-good files from earlier runs do not substitute for that first complete run. After a manifest has been published, a per-program recent success must not make an incomplete run appear fresh. If a later run cannot assemble or publish a replacement, retain the old artifact but report `degraded` in the manifest when writable. If a manifest write fails, alert independently and clients detect its old timestamp as overdue. Define these fields and precedence in the public manifest documentation.
- Every scheduled or manual workflow run that actually starts downloads and rebuilds **every in-scope program**. Do not use `HEAD`, `ETag`, `Last-Modified`, or other no-change checks to skip downloads or rebuilding. Download source files afresh, record their identifiers and SHA-256 checksums, and validate each program independently. A 404, empty source, unparseable source, unexpected schema, or failed validation is a program failure, not evidence that the program should be removed.
- Keep a durable compact last-good Parquet file for each program in the currently published required scope in R2. Store per-program and combined files at immutable content-addressed paths; verify uploads by reading them back and checking checksums. Before the first public catalog, require a newly validated file for every program proposed for initial publication from that same run and assemble only those files. After first publication, assemble the current-scope candidate from newly validated files for successful programs and last-good files for failed current-scope programs. A future-milestone addition stays proposed/in build scope until its own new file passes per-program validation and a combined candidate containing it passes validation; never substitute a failed addition's last-good file to claim it is included. If a currently published required program lacks the needed valid file, do not publish a replacement. A program disappears from published scope only through an explicit human-authorized scope change; a missing, empty, malformed, or otherwise failed source never removes it automatically. No automatic removal decision criteria are introduced here.
- Publish the combined artifact only after all per-program files selected for it and the combined candidate pass validation. Upload and verify immutable data objects first; switch `latest.json` last. Keep the existing artifact pointer if candidate assembly or validation fails, but update run status and error details when possible. After the first publication, a partial but valid combined candidate may be published using last-good copies, and its manifest must clearly mark the overall catalog degraded (or stale under the policy above).
- In the same atomic `latest.json` write that switches `current` and its published program list, set `previous` to the complete prior `current` record: combined artifact URL, SHA-256, byte size, build time/schema version, exact included program list, and for every included program its immutable file URL, SHA-256, source input checksums, and source-built time. Set `previous.expires_at` to the end of a documented rollback/cache-propagation grace period. First publication has no `previous`. Keep last-good files for the current published scope and every object referenced by `current` or unexpired `previous`. Cleanup runs under the same serialization lock, rereads the manifest immediately before deletion, derives protected object keys from `current`, unexpired `previous`, and current-scope last-good records, and deletes only other objects whose grace period has elapsed. Expiry only removes `previous` from protection after its timestamp; it does not itself delete objects. To roll back during the grace window, verify the previous combined and all per-program checksums, then atomically make that exact record `current` and make the displaced `current` the new `previous` with a fresh grace expiry. Never roll back to an expired or unverified record; if rollback is needed after expiry, republish only after verifying the retained artifact and exact file references, creating a new `previous` snapshot as part of that manifest write. This is not a historical archive.
- Provide a documented build command, pinned dependencies, fixtures, automated tests, validation report, and an operational runbook (credentials, manual rebuild, rollback, alerting, and expected costs). Never commit R2 credentials or raw BLS bulk files. GitHub Actions artifacts are temporary diagnostics only, never durable source or publication storage; R2 holds durable per-program files and public artifacts.

The research scoped 54 programs and about 9.48 million series: 30 programs with native titles in full; 24 without native titles requiring title synthesis; exclude `nw` and the ten case-characteristics tier-3 programs initially. v1 covers the 30 native-title programs plus the three live untitled programs (`sm`, `jt`, and `pr`); the other 21 untitled programs follow in later releases. Re-check the directory list and counts at build time. The estimate of ~50 MB for a compact Parquet file is **not a measured v1 deliverable**: measure final bytes, download time, validation and workflow usage, and local query performance.

## Work sequence

### 1. Establish the reproducible ingest

- Choose a maintainable build language and pin a runtime plus dependencies; keep the pipeline independent of the `epidatatools` package. Document one local build invocation used unchanged in CI.
- Inventory in-scope BLS `.series` files and the lookup files needed for untitled programs. Fetch all inputs via HTTPS for every scheduled or manual workflow run that actually starts, with a descriptive, contactable User-Agent, bounded concurrency, retries with backoff, and sensible timeouts. Do not use conditional requests or header checks to skip a full download or rebuild. Record source URL, response metadata where available, byte size, and SHA-256 per input. Raw source files are temporary and are not durable between runs. Download to temporary files and verify complete responses before parsing. Validate each program's inputs as a consistent build unit: after downloading, recheck the identity of every input, including `.series` files. Compare trustworthy source validators where available; otherwise download again and compare SHA-256 hashes. If an input changed during the build or a response is incomplete, retry that program's full set of inputs up to a fixed limit, then mark it failed. A header alone is not proof of unchanged bytes unless its reliability for that source has been established.
- Normalize per-program schemas explicitly; fail on unexpected layouts instead of silently shifting fields. Cover anomalies recorded in the research (`cc` concatenated header/row; extra trailing fields in `eb`, `ec`, `ee`, `gp`, `hs`, `pd`, `sa`, `sh`, `si`; `hs` shifted year columns; `kv` without year fields). Trim padded IDs and validate that IDs and decoded dimensions are plausible. Keep provenance for every row.
- Build and review titles in checkpoints, with the native-title checkpoint completed before any title synthesis:
  1. Validate the 30 native-title programs (`ap`, `bd`, `ce`, `ci`, `cm`, `cu`, `cw`, `cx`, `ei`, `ep`, `fm`, `ip`, `is`, `kv`, `la`, `le`, `ln`, `lu`, `mp`, `nb`, `nd`, `oe`, `or`, `pc`, `su`, `tu`, `wd`, `wm`, `wp`, and `ws`). Preserve native title text; duplicate titles are allowed.
  2. Implement and validate synthesized title templates for the live untitled programs `sm`, `jt`, and `pr`. This completes v1's 33 programs.
  3. Add frozen twins of titled programs: `ee`, `sa`, `mu`, `mw`, `pd`, `cc`, `ec`, `nc`, `eb`, and `jl`.
  4. Add injuries and illnesses: `ii`, `sh`, `hs`, and `si`.
  5. Add standalone frozen programs: `ml`, `gp`, `in`, `gg`, `bp`, `li`, and `bg`.

  For synthesized titles, check that every series matches exactly one row in each required lookup table, no labels are missing, synthesized title counts equal `.series` row counts, and representative known series match BLS descriptions. Duplicate output titles are permitted; validate series IDs and lookup cardinality instead. Each release's coverage counts list the programs it includes; do not describe a release as covering all 54 programs until checkpoint 5 passes.

### 2. Define and test the catalog semantics

- Set documented rules for seasonal adjustment and missing metadata. Preserve frozen, still-listed series. Do not infer live/frozen status from `end_year` or `end_period`; no first-seen/last-seen state store is required. Current-source disappearance alone does not remove a required program; it is handled as a failed program and the last-good copy is retained until an explicit human-authorized scope change.
- Enforce verified uniqueness of series IDs (or document and test any genuine cross-program collision), nonempty titles, valid program assignments, sensible years, and predictable nulls. Do not require title uniqueness. Reject unexpected row-count drops, program omissions, title-join explosions, malformed text, or missing required columns; thresholds should be explicit and require investigation rather than masking genuine BLS changes. An empty program input is a failure, not a valid removal.
- Compare representative IDs against BLS files and, where feasible, the BLS data API: common unemployment/CPS, CES, CPI, JOLTS, and OEWS cases; include frozen and removed-from-source cases. Verify that a program failure uses the last-good file, a missing last-good blocks publication, a partial catalog is marked degraded, and aggregate validation failure leaves the public artifact pointer untouched.
- Benchmark search on a downloaded local file for realistic queries, including `unemployment` and an OEWS occupation, with a survey restriction and seasonality filter. Document that free-text search semantics and relevance ranking belong to consuming clients unless a common search specification is deliberately added later. Avoid claiming subsecond searches or a particular artifact size until measured.

### 3. Automate builds without operating a server

- Use one scheduled GitHub Actions workflow in a public `bls_index` repository on a standard Linux runner, scheduled daily and also supporting manual dispatch. Put both triggers in the same concurrency group (`group: bls-index-publish`, `cancel-in-progress: false`): a running job is not canceled, but GitHub Actions may replace an older pending request with a newer pending request, so not every trigger is guaranteed to run. This coalescing/replacement is permitted for scheduled and manual requests. Operators can see canceled pending runs in GitHub Actions; if a manual run is replaced and its work is still needed, trigger it again. Only runs that actually start execution are attempts; a request canceled before starting must not be recorded as a failed attempt or update per-program attempt/status records. Each started run downloads and rebuilds every required program. Manual rebuilds go through that workflow, not local machines, so they share the lock. Test actual memory, disk, runtime, BLS network access, and dependency setup. Measure daily Actions minutes, data transfer, and total usage against the applicable GitHub usage caps; configure usage monitoring/alerts and adjust the run only if needed to remain within caps. The research's few-minute full rebuild is an estimate, not a promise. Cloudflare Workers Cron is not the bulk build environment.
- Every workflow run that actually starts downloads, rebuilds, and validates every currently published required program independently, regardless of whether BLS headers or identifiers appear unchanged; proposed additions are also built for evaluation but remain outside published scope until promoted. Upload successful compact per-program files to immutable R2 keys and read them back to verify checksums. Before the first public publication, any failed program proposed for initial inclusion blocks publication even if a last-good file exists; record the failure in the GitHub Actions run and alert maintainers independently. Publish the first combined artifact and `latest.json` only after every program proposed for initial inclusion succeeds in that same run and the combined candidate passes validation. After publication, select last-good files for failed programs in the currently published scope, assemble and validate the candidate, calculate its SHA-256 and size, and produce a machine-readable validation summary. A failed or invalid proposed addition is excluded from the candidate and the public program list; if the combined candidate containing a successfully validated addition fails, do not promote it or change the published list. If any currently published required program lacks a valid copy, do not replace the existing artifact. On a valid candidate, upload and verify immutable data objects, then atomically write `latest.json` with the new `current`, its exact included program list, and `previous` equal to the complete prior `current` record with a new grace expiry. Update attempt records and overall freshness state for every started run where the manifest is writable. A request canceled before starting is not a failed attempt and must not update those records. GitHub Actions artifacts may contain temporary logs only; do not rely on them for last-good data, rollback, or publication.
- Alert maintainers on program/build/publication failures and on stale or overdue status. Manifest publication failure is a separate alert condition: attempt an independent notification through the workflow/monitoring path, because the manifest cannot report its own failed write. If status cannot be published, clients detect the old `manifest_updated_at` as overdue. The artifact pointer remains on the last valid catalog when no valid replacement can be assembled or validated.
- Keep source and catalog ages visible. The 48-hour overall stale threshold allows a missed daily run but does not imply that a partially rebuilt catalog is fresh. Frozen datasets are downloaded and rechecked every run like live ones. Document upstream outage behavior and the per-program fallback policy.

### 4. Serve safely and cheaply

- Store the Parquet files and manifest in an R2 **Standard** bucket exposed through a dedicated Cloudflare custom domain; turn off the public `r2.dev` URL so security/cache rules cannot be bypassed through it. No API keys for read access; downloads must work from non-browser tools such as R and `curl` without JavaScript challenges.
- Configure a narrow Cache Rule for immutable `.parquet` paths (not all site traffic), with a long TTL; configure a short TTL for `latest.json` so publication and status changes propagate promptly. Check `Cache-Control`, `ETag`, `Content-Length`, and actual cache hit/miss behavior after launch. `.parquet` is not cached by Cloudflare by default. Avoid cookies or arbitrary query strings in published URLs that fragment the cache.
- Add a conservative per-IP, path-scoped WAF rate-limit **block** rule only after measuring legitimate traffic; leave room for shared institutional IPs. Do not use CAPTCHA/Managed Challenge for the machine-readable download. Add usage and budget alerts, understanding that alerts are not hard cost caps. Document that caching and rate limiting mitigate abuse but do not guarantee a maximum bill. Revisit protections using measured R2 Class B reads and edge hit rates.
- Verify cold download, repeated download, checksum validation, manifest refresh after complete and partial runs, rollback, and old-file cleanup from an external machine. Test both fresh and cached requests and a failure/rollback path. Keep the catalog within the chosen CDN's cacheable size limit or revise serving strategy.

## Interface reserved for future `epidatatools` integration

Publish `data-dict.yaml`, schema and manifest examples, a checksum verification example, a small fixture, and the stable manifest URL. The future client can check the manifest at a documented interval, fetch a new file once to `tools::R_user_dir("epidatatools", "cache")`, verify the checksum and supported catalog schema version, check essential columns/types, swap the cache atomically, and search locally/offline afterward. It does not need the `data-dict` CLI or a full-row validation scan at runtime. Expose catalog source and age to callers, and treat the catalog as stale when the manifest says stale or its update timestamp is over 48 hours old. Consumers must not interpret `degraded` as fresh just because the manifest itself was recently updated. This integration, its user-consent/download UX, API compatibility, CRAN checks, and relevance ranking are **out of scope for this repository**; do not make the index build depend on `epidatatools`.

## Decisions

- **Rebuild all required programs daily and validate independently** (roborev job 8). Do not skip work based on `HEAD`, `ETag`, or `Last-Modified`. These values may be recorded as source metadata, but every scheduled or manual workflow run that actually starts downloads and rebuilds every in-scope program. A pending request canceled before starting is not an attempt and does not update per-program attempt/status records.
- **Separate published programs from proposed additions** (roborev job 10). The manifest's required program list and coverage describe only programs actually included in `current`. Later milestone programs remain proposed/in build scope until each passes per-program validation and a combined candidate containing it passes; a failed addition is never represented as included or substituted with a last-good file. Switch the published scope only atomically with that passing artifact. An upstream failure never removes a currently published program; scope removal requires explicit human authorization, and this design does not prescribe removal criteria.
- **Use per-program last-good files and publish the combined catalog from valid copies** (roborev job 8). Each program is an independent validation unit. The first public catalog requires every program proposed for initial inclusion to succeed in the same run; do not use older last-good files to make that initial publication. After the first publication, a failed currently published program may use its durable last-good file in a partial combined publication; if it has no valid copy, retain the previous combined artifact. A bad or absent source never implicitly removes a published program.
- **Publish immutable files before switching the manifest and snapshot rollback state** (roborev job 10). For first publication, verify successful same-run files for every proposed initial program and the assembled combined file, then publish the combined artifact and write `latest.json` last. For every later artifact switch, the same atomic manifest write updates `current` and the included program list and sets `previous` to the full prior `current`, including its combined URL/checksum and exact per-program file URLs/checksums, with a documented grace expiry. Cleanup rereads the manifest under the serialization lock and protects `current`, unexpired `previous`, and last-good records; expiry removes rollback protection but does not itself delete data. Rollback within the grace period verifies all checksums and atomically swaps the records, renewing the grace period for the displaced current; after expiry, rollback requires re-verification and republishing as a new switch. If the manifest write fails, alert independently and rely on its overdue timestamp for client detection.
- **Distinguish complete verification, mixed freshness, and stale status** (roborev job 8). Only an artifact made from every program in its published required scope validated in the same complete run, within 48 hours, may be called fresh. A failed proposed addition is not represented as part of the published catalog; any fallback for a published program makes it degraded. More than 48 hours since the last complete successful source verification makes the catalog stale. An overdue manifest is also stale to clients. Keep per-program timestamps and attempt outcomes visible; do not let a recent successful subset overwrite the timestamp for the last complete run.
- **Do not require title uniqueness; finish the native-title checkpoint before synthesis** (roborev job 8). Native BLS titles may duplicate, so enforce series/lookup correctness rather than unique title strings. Validate the 30 native-title programs first, then implement synthesized titles for the three live untitled v1 programs.
- **Keep series liveness out of v1** (roborev job 8). The catalog describes which series are present in the current BLS source; it does not decide whether a series is active. `end_year` and `end_period` are not liveness signals. Freshness describes source verification and publication health, not series liveness.
- **Serialize one GitHub Actions workflow and keep durable data in R2** (roborev job 8). Daily scheduled and manual runs use the same GitHub Actions concurrency group with `cancel-in-progress: false`: a running job continues, while a newer pending request may replace an older pending request. This coalescing is permitted for both scheduled and manual requests; not every trigger is promised to run. Operators can see canceled pending runs in GitHub Actions; if a manual run is replaced and its work is still needed, trigger it again. Only runs that start count as attempts and update per-program attempt/status records; canceled-before-start requests are not failed attempts. Each started run does a full rebuild. Measure actual usage against GitHub caps. GitHub Actions artifacts are not durable; R2 holds last-good program files, public combined files, and rollback inputs.
