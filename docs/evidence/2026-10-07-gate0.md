### data-dict

`data-dict-yaml==0.0.3` from PyPI installs the `data-dict 0.0.3` binary into the uv
environment; `tests/test_toolchain.py` checks the version and that `validate-spec`,
`validate-meta` and `validate-data` exist and accept `--json`. The specification
(`data-dict spec`, spec `$version` 0.1.0) supports column constraints `required`,
`unique` and `primary_key`, `enum` value sets, and SQL-style `assert` expressions
(rows pass when the expression is true or null). `validate-data` reads the Parquet path
from the dictionary's `source.parquet`, so validating each candidate needs a dictionary
copy (or path) pointing at that candidate; Phase 1 settles this.

## Local object store: moto server

No container runtime is available on the development machine, so the local
S3-compatible service is moto's threaded server (pure Python; same in CI). Checked
directly against moto 5.2.3:

| Operation | Result |
|---|---|
| `PutObject` with `If-None-Match: *`, key absent | 200, committed |
| Same, key present | 412 `PreconditionFailed` |
| `PutObject` with `If-Match: <current ETag>` | 200, committed |
| `PutObject` with `If-Match: <stale ETag>` | 412 `PreconditionFailed` |
| `PutObject` with `If-Match`, key absent | 404 `NoSuchKey` |
| `GetObject`, key absent | 404 `NoSuchKey` |
| `HeadObject`, key absent | 404 (no error body) |

moto is in-memory and strongly consistent. It cannot show R2's behavior under
concurrent writers, replication delay, or delayed in-flight requests, so it does not
establish the semantics the manifest protocol needs. Those remain staging checks against
real R2 (plan: "Do not claim an unverified R2 API guarantees these semantics").

## Findings that changed the code

1. **botocore retried "non-retried" requests.** `retries={"max_attempts": 1}` means one
   *retry*. The fault-injection harness caught it: an injected 500 on `GetObject` was
   silently retried. For a conditional manifest write, a retry after a committed write
   with a dropped response returns 412 and would be misread as a confirmed rejection.
   The adapter now uses `total_max_attempts: 1`, and
   `test_commit_then_dropped_response_is_unknown_and_not_retried` asserts that exactly
   one PUT reaches the store.
2. **A HEAD 404 cannot distinguish a missing key from a missing bucket**, and could be
   spurious. `stat()` treats a HEAD 404 as absence only when a follow-up `GetObject`
   reports `NoSuchKey`; if the GET finds the object or fails, it is an error. `read()`
   requires the `NoSuchKey` code. Phase 2's manifest reader should use `GetObject` for
   the absence check.
3. **BLS serves most `.series` files without `Content-Length`.** 30 of 51 inputs (every
   `.series` file except `pr`, `su` and `ws`) arrived with no declared length; all
   lookup files declared one. Truncation detection for them relies on
   the missing terminal chunk, which the fetcher classifies as `incomplete`. The harness
   now serves chunked bodies and truncates them mid-stream
   (`test_truncated_chunked_body_is_incomplete`). The download-twice SHA-256 comparison
   is a second guard, but would not catch two identical truncations.
4. **BLS rejects any User-Agent containing "github".** Checked by hand on 2026-10-07
   against `pr.series`: `test github` and `test (+https://github.com/)` returned 403, while
   the same forms with `gitlab.com` or `example.com` returned 200, as did
   `bls-index catalog builder (+https://www.epi.org/; <email>)`. The planned agent with
   the repository URL was therefore unusable. `validate_user_agent` now rejects such
   agents, and the `source-probe` workflow reads the agent from a repository secret.
5. **Request pacing.** The BLS robot policy allows blocking robots that request
   "multiple times per second"; the first probe could briefly exceed that on small lookup
   files. The fetcher now spaces request starts at least `min_request_interval` (default
   1 s) apart across all workers. A paced real probe of `sm`, `jt`, `pr` and `ap` made 44
   requests, all 200, at least 1.0 s apart, in 43 s.

## Adapter classification (provisional, pending staging)

- Writes: 2xx → `committed`; 412, or 404 `NoSuchKey` on `If-Match` → `rejected`;
  everything else (5xx, 403, 409 `ConditionalRequestConflict`, other 404s such as
  `NoSuchBucket`, timeouts, dropped connections before or after the request) →
  `unknown`. 403 and a pre-send connection failure are probably
  non-commits, but the plan only permits non-commit when storage guarantees it, so they
  stay `unknown` and require reconciliation.
- Reads: `NoSuchKey` → confirmed absence; 403, 5xx, `NoSuchBucket`, timeouts, dropped
  connections, short bodies → error.
- Immutable uploads use create-if-absent; an existing key returns `rejected` and the
  caller must still read back and verify SHA-256 before referencing it.

## Real BLS probe (developer machine, not a clean runner)

Run: `bls-index probe --programs initial --parse-check`, 2026-10-07 04:16–04:18 UTC,
User-Agent `bls_index catalog builder (+https://www.epi.org/)`, concurrency 4. Machine:
8 CPUs, 33 GB RAM.

- **All 33 programs succeeded** on the first input-set attempt; every input's recheck
  SHA-256 matched.
- **8,315,248 `.series` rows**; 1.66 GB downloaded once (3.32 GB with the recheck);
  90 s wall clock, including parsing every `.series` with polars.
- A User-Agent with an organization URL and no email address returned 200.
- All files use CRLF line endings, decode as UTF-8, have no blank lines, and every
  `.series` data row has exactly the header's field count. `pr.seasonal` has one blank
  trailing line.
- ETag and Last-Modified were identical across the two reads. The ETag looks like an
  IIS timestamp form (`"030991e73e4dc1:0"`), not a content hash. Validator reliability is
  **not** established, so daily builds keep redownloading and comparing SHA-256.
- Lookups for `sm`, `jt` and `pr`: every code column in each `.series` header maps to
  exactly one configured lookup file, and every configured lookup has a matching
  column (`scope.LOOKUP_FILES`).

Largest inputs and the polars feasibility parse (all columns as strings, whole file in
memory, fresh process):

| Program | Rows | MB | Parse s | Peak RSS MB |
|---|---:|---:|---:|---:|
| `oe` | 6,023,970 | 1,261.4 | 1.38 | 4,258 |
| `is` | 891,324 | 125.7 | 0.20 | 553 |
| `wm` | 557,753 | 108.5 | 0.19 | 477 |
| `cx` | 183,935 | 31.1 | 0.06 | 186 |
| `ep` | 113,898 | 18.6 | 0.04 | 136 |

**Peak memory for `oe` (~4.3 GB) is the number to check on the runner.** It fits a
16 GB runner but is uncomfortable on a 7 GB one once the build holds other state. If the
clean-runner probe shows tight memory, Phase 1 should project only the needed columns or
use polars' lazy/streaming reader for `oe`. That decision belongs after the runner
measurement, per the plan.

now versus 8,287,846 native + 25,269 untitled = 8,313,115 measured 2026-08-11.
