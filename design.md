# Plan: build and publish a current BLS series catalog

## Purpose and boundary

This is a **standalone `bls_index` project**. Build a reproducible, current, downloadable index of BLS series IDs and searchable titles from the official flat files at `https://download.bls.gov/pub/time.series/`. Do not implement or change `epidatatools` here. A future `epidatatools::find_bls()` may download the published file into a user cache and search it locally; the index must therefore have a documented, stable file format and discovery mechanism. No hosted query API, browser UI, SQLite-over-HTTP, or DuckDB remote range-read requirement for v1.

“Current” means **present in the latest successfully ingested BLS `.series` files**, not necessarily still receiving observations. Frozen but still-listed series belong in the catalog. The catalog's source-verification freshness is separate from series liveness: do not infer that a series is live or frozen from its year or period fields, and never describe a failed, mixed, or overdue build as a fresh complete snapshot. The research note `research/2026-08-11-existing-bls-series-catalogs.md` is the starting inventory, not a substitute for validating current BLS files.

## Deliverable and contract

- Publish one canonical, compressed `bls_index.parquet` per assembled publication, served at an immutable `bls_index-<sha256>.parquet` URL. Start with a flat search schema: `program`, `series_id`, `series_title`, `title_source` (`native`/`synthesized`), `seasonal` (SA/NSA/unknown), `begin_year`, `end_year`, and `end_period`. v1 has no series-level liveness `status`; year and period fields describe source metadata only. Include `survey_name` and `begin_period` if verified and useful; nullable values must stay nullable rather than be guessed. Specify types, normalization, and schema version in documentation. Keep IDs as strings, trim BLS padding, and preserve the original BLS title when supplied. Do not treat BLS survey/program codes as interchangeable without an explicit mapping.
- Maintain a repository-root `data-dict.yaml` (the documented data-dict naming convention) with `name: bls_index` and a Parquet source pointing to the local `bls_index.parquet`. Define column meanings and types, nullable fields, allowed categorical values, and machine-checkable constraints (including required IDs/titles and verified ID uniqueness). Native titles are not required to be unique: distinct series may share a title. Do not use title uniqueness as a validation condition. Pin the `data-dict` CLI version; run `validate-spec`, `validate-meta`, and `validate-data` on every combined publication candidate in CI. The dictionary's `$version` identifies the data-dict specification, separately from this catalog's own schema version. Measure full-data validation cost and keep nonexpressible BLS-specific checks in the build tests. Keep the authoritative dictionary in the repository; if also publishing it beside the artifact, arrange a stable source path (or generate a publication copy pointing to the immutable artifact) and validate that copy. Runtime clients do not need the CLI.
- Publish a small `latest.json` manifest only with the first combined catalog, after every program in the fixed initial scope has succeeded in the same run and the combined candidate passes validation. The initial scope is the repository's defined 33 programs: the 30 native-title programs plus `sm`, `jt`, and `pr`. Until that first publication, neither `latest.json` nor a published combined catalog exists; immutable uploads may nevertheless be publicly retrievable at known URLs as unreferenced orphans. Failures before a manifest write, and confirmed non-commits reconciled to manifest absence, leave no published catalog; an unknown first-write outcome must be reconciled before claiming whether publication occurred. Record started failures and alert independently. An initial attempt has no last-good fallback: all 33 must pass in that same run. Once published, the manifest identifies `current` combined artifact (schema version, immutable URL, SHA-256, byte size, and artifact build time) and its exact per-program files (immutable R2 URL and SHA-256, plus source input checksums and source-built time). Every object reference in the manifest (combined, per-program, `previous`, and last-good) is a path relative to the manifest's own URL, resolved by standard URL reference resolution (RFC 3986): for example `bls_index-<sha256>.parquet` or `programs/ap-<sha256>.parquet` beside `/v1/latest.json`. The manifest names no host. Each reference must be a normalized path-relative reference: no scheme or host, no leading `/`, no `.` or `..` segments, no query, and no fragment, so it always resolves on the manifest's host under the manifest's `/v1/` directory. Builds and clients reject any other form. Wherever this design says the manifest records an object's URL, it means this relative path. Its public `required_programs` list and coverage counts describe exactly the programs included in `current`. It also records `scope_revision`, initialized at first publication and incremented atomically only when a successful scope release changes `required_programs`; daily artifact and status writes do not change it.
- **Daily scope comes only from the published manifest.** Each scheduled daily run reads `required_programs` from `latest.json` and downloads, rebuilds, and validates only those programs. It must not derive or extend daily scope from the repository's list of future milestone programs, source-directory contents, successful exploratory builds, or a proposed-program list. Before the first manifest exists, the daily initial-publication run uses the fixed initial 33-program scope in the repository; it publishes nothing unless all 33 pass in that same run and the combined candidate passes. Future milestones are documentation/planning only and are not automatically built or promoted.
- A change to published scope after the first publication is rare and requires an operator to explicitly invoke the serialized GitHub Actions scope-release workflow/action with an approved exact `target_programs` list. Before first publication, scope release is unavailable: the initial catalog must use the fixed repository-defined 33-program scope. Before downloading, validate the operator-supplied target list: it must be nonempty, contain unique canonical codes supported by implemented and tested builds, and be compared exactly with the currently published list to show additions and removals. Require explicit operator confirmation of that exact change set, bound to a base-scope fingerprint consisting of the manifest's monotonically increasing `scope_revision` and exact canonical current `required_programs` list; increment `scope_revision` whenever a successful scope release changes that list, and do not change it for daily artifact or status writes. Reject unknown, duplicate, empty, unconfirmed, or otherwise unintended contractions without starting downloads. The approval policy is required, but this design does not prescribe a particular approval mechanism. After confirmation, validate **every target program** from fresh source inputs in that same run, without last-good fallback for any target program, then validate a combined candidate for the full target. Scope expansion, reintroduction, and contraction/removal all require this explicit release; no scheduled run or source change interprets an absent program or a 404 as a scope-change request. On success, upload and verify immutable program and combined objects, then atomically publish the new artifact and its exact `required_programs` list together in `latest.json`, with the old `current` saved as `previous`. In that same write, set `last_complete_successful_source_verification_at` to this run's verification time for the entire resulting target scope, and replace last-good records with records for every target program pinned to its corresponding newly validated immutable file, including its source-built time and checksum; discard last-good records for programs outside the target. Thus a later daily failure for a target program falls back to the file validated by this release. A release validation or other pre-switch failure does not attempt to switch the artifact pointer or scope; log and independently alert it. If the switch is attempted and its response is rejected or unknown, use the manifest write outcome protocol before describing state, retrying, or making any further mutation. A failure confined to a proposed target program does not change the current published artifact, scope, or status. A scope-release validation/pre-switch failure or confirmed non-commit never advances `last_complete_successful_source_verification_at`; an unknown switch outcome must be reconciled before asserting whether it advanced. If validation fails for any currently published program included in the release attempt, record/report that current-scope failure and, if the manifest is writable, set published status to degraded unless stale takes precedence; retain the prior complete-verification time. A failure confined solely to target-only programs leaves published status unchanged. Before the first publication, release failures have no manifest status to update and are reported in the workflow and independent alert.
- The manifest also records each program's most recent attempt time, outcome, and error; its last-good file reference and time; and whether the current combined artifact used a newly validated file or a last-good file, while keeping attempt records distinct from claims about published coverage. An attempt is a workflow run that actually starts execution; requests canceled while pending do not count as attempts and must not be reported as failed attempts or update per-program attempt/status records. Keep artifact identity separate from check/status fields, which are updated for each started daily run where the manifest is writable.
- The manifest records `last_complete_successful_source_verification_at`: the time of the most recent run in which every program in the published scope passed source download, parsing, and per-program validation. For a daily run, evaluate the currently published `required_programs`; for a successful scope release, evaluate the full resulting target scope and advance this timestamp in the same atomic write that publishes it. Programs outside the scope being verified neither block nor advance it. Each `current`/`previous` artifact record also retains that scope's actual last-complete-verification timestamp, so rollback restores the historical value rather than inventing a new verification time. Also record `last_attempt_at`, `manifest_updated_at`, and a clear overall status. Status precedence is `stale` first, then `degraded`, then `fresh`: stale means the last complete successful source verification for the published scope is older than 48 hours, or clients find `manifest_updated_at` older than 48 hours; degraded means the latest daily run did not fully validate every currently published required program, a scope-release attempt failed to validate a program in the currently published scope, the published catalog uses any last-good fallback, or the catalog was rolled back and is awaiting a new complete successful rebuild of its restored published scope; a failed scope release affecting only programs outside published scope does not degrade the current catalog even though no replacement was published. Fresh is permitted only when the latest successful daily run or scope release fully validated every program in the resulting published `required_programs` without fallback, the published artifact uses those newly validated files, the complete-verification timestamp corresponds to that run, and the run is within 48 hours. A failure confined to programs outside published scope during a manual release does not change the current scope's status. If a release attempt fails validation for any currently published program, set published status to degraded unless stale takes precedence, where the manifest is writable; it does not advance complete verification. Before the first public publication, no manifest exists to carry a status: failed attempts are recorded in the GitHub Actions run and trigger an independent maintainer alert. After a manifest has been published, a per-program recent success must not make an incomplete current-scope run appear fresh. If a later daily run cannot assemble a replacement before attempting a switch, retain the old artifact and report `degraded` through a separately reconciled status write when safe. If an attempted switch has an unknown outcome, do not assume the old artifact remains current or write status until authoritative reconciliation resolves it. For every failed or uncertain manifest write, follow the manifest write outcome protocol and alert independently. Clients can identify an overdue manifest only from the timestamp they actually read; an unknown write outcome does not prove that the old manifest remains current. Define these fields and precedence in the public manifest documentation.
- Every scheduled or manual **daily rebuild** that actually starts downloads and rebuilds every program in the currently published `required_programs` list (or all 33 fixed initial programs before first publication). Do not use `HEAD`, `ETag`, `Last-Modified`, or other no-change checks to skip downloads or rebuilding. Download source files afresh, record their identifiers and SHA-256 checksums, and validate each program independently. A 404, empty source, unparseable source, unexpected schema, or failed validation is a program failure, not evidence that the program should be removed. A scope-release run first validates a nonempty, unique list of canonical supported program codes and compares its exact additions and removals with the current published list; the operator must explicitly confirm those exact changes, including any contraction, bound to the base-scope fingerprint (`scope_revision` plus the exact canonical current `required_programs` list), before any download starts. Recheck that fingerprint immediately before downloads and immediately before the atomic manifest switch; if it changed, abort without a scope switch and request fresh approval. Reject unknown, duplicate, empty, unconfirmed, or unintended contractions without downloading. The approval policy is required, but no particular mechanism is prescribed. After confirmation, rebuild every target program from fresh inputs; never substitute the daily published-scope list for the release target.
- Keep a durable compact last-good Parquet file for each program in the currently published required scope in R2. Store per-program and combined files at immutable content-addressed paths; verify uploads by reading them back and checking checksums. Before the first public catalog, require a newly validated file for every initial-scope program from that same run and assemble only those files. After first publication, the daily run assembles the current-scope candidate from newly validated files for successful programs and last-good files for failed current-scope programs. If a currently published required program lacks the needed valid file, do not publish a replacement. A scope-release run never uses fallback: every target program must succeed in the same run, and the full target combined candidate must pass validation before a switch is attempted. Any attempted switch follows the manifest write outcome protocol. Only after that success does the atomic manifest write advance complete verification for the resulting target scope and pin each target's last-good record to its newly validated file, source-built time, and checksum, discarding out-of-target last-good records. The only way to add, reintroduce, or remove a program from published scope is a successfully reconciled, explicitly authorized scope-release manifest write. A missing, empty, malformed, or otherwise failed source never removes a program automatically. If a release switch outcome is unknown, reconcile it before claiming that scope and artifact pointers were unchanged. This design does not introduce automatic removal criteria; operators must approve and supply the target list for any contraction.
- Publish a daily combined artifact only after all per-program files selected for it and the combined candidate pass validation. For a scope release, publish only after every target program succeeds without fallback and the combined target candidate passes. Upload and verify immutable data objects first; switch `latest.json` last. If daily candidate assembly or validation fails before a switch is attempted, keep the existing artifact pointer and update run status/error details only through a separate manifest mutation governed by the write outcome protocol. For a switch with a rejected or unknown response, reconcile before claiming which artifact is current or attempting any status mutation. After the first publication, a partial but valid daily current-scope candidate may be published using last-good copies, and its manifest must clearly mark the overall catalog degraded (or stale under the policy above). A pre-switch scope-release failure or confirmed non-commit does not replace the published artifact or scope; an unknown switch outcome must be reconciled before asserting state. Failure confined solely to target-only programs does not alter published status, while validation failure for any currently published program included in the release attempt may set published status to degraded unless stale takes precedence, through a separate safely reconciled manifest write, as described above.
- In the same atomic `latest.json` write that switches `current` and its published program list, set `previous` to the complete prior `current` record: combined artifact URL, SHA-256, byte size, build time/schema version, exact included program list, each included program's immutable file URL, SHA-256, source input checksums and actual source-built time, and that scope's actual `last_complete_successful_source_verification_at`. Set `previous.expires_at` to the end of a documented rollback/cache-propagation grace period. First publication has no `previous`. Keep last-good files for the current published scope and every object referenced by `current` or unexpired `previous`. Cleanup runs under the same serialization lock, rereads the manifest immediately before deletion, derives protected object keys from `current`, unexpired `previous`, and current-scope last-good records, and deletes only other objects whose grace period has elapsed. Expiry only removes `previous` from protection after its timestamp; it does not itself delete objects. An ordinary rollback is allowed only to a verified `previous` record whose exact `required_programs` scope matches the currently published scope. Verify the previous combined and all per-program checksums, then in one atomic manifest write make that exact record `current` and make the displaced `current` the new `previous` with a fresh grace expiry. Do not use ordinary rollback to switch to a different scope or reverse a rollback across scopes; expansion or reintroduction requires a new explicit scope release, and contraction likewise requires an explicit release. In that same rollback write, reset/pin each restored-scope program's last-good reference and time to the exact immutable per-program file and actual source-built time in the restored artifact; do not allow a displaced-version file to be selected as fallback for any restored program until that program has successfully rebuilt and validated a new file. Preserve only last-good records for the restored scope; `previous` protects references for the grace period. Restore the record's actual source-built times and scope-verification timestamp; do not change them to the rollback time, carry forward a fresher status from the displaced artifact, or treat checksum verification as a new source verification. Mark the restored catalog `degraded` until a new complete successful rebuild of its restored published scope; if its restored verification timestamp has crossed the 48-hour threshold, `stale` takes precedence. Never use an expired `previous` record for rollback. If recovery after expiry is required, independently verify the retained artifact and exact per-program references, then publish it as a newly verified same-scope candidate only if its scope matches the currently published scope, snapshotting the displaced `current` as a new `previous` in the same manifest write. This recovery path cannot change scope; use an explicitly approved scope release for that. This is not a historical archive.
- Provide a documented build command, pinned dependencies, fixtures, automated tests, validation report, and an operational runbook (credentials, daily rebuild, explicit scope release, rollback, alerting, and expected costs). Never commit R2 credentials or raw BLS bulk files. GitHub Actions artifacts are temporary diagnostics only, never durable source or publication storage; R2 holds durable per-program files and public artifacts.

## Manifest write outcome protocol

Apply this protocol to every manifest mutation: first publication, daily artifact or status update, scope release, rollback, and post-expiry recovery. Use one authoritative, durable operation journal at a configured private location that is not publicly readable and is not subject to artifact cleanup. The journal is a conditionally updated index containing the full intended manifest content, unique `manifest_write_id`, exact expected prior manifest version (including expected absence), and lifecycle state for each operation. Before attempting the manifest write, durably append a `prepared` entry to that index using a conditional create-if-absent/CAS against its exact authoritative version. Do not submit the manifest write unless the prepared entry is confirmed durable; an uncertain journal write must itself be reconciled through an uncached authoritative journal read, and an inconclusive result blocks submission. Immediately before dispatch, durably transition the entry from `prepared` to `submitting` by conditional update; do not dispatch unless that transition is confirmed durable. A record still `prepared` after a crashed serialized run proves no manifest request was dispatched, so it can be durably resolved non-committed. A `submitting` entry means the request may or may not have reached storage and must be reconciled; an old-state read proves non-commit only under tested semantics that exclude a delayed/in-flight request. Include the identity in the manifest and issue only a conditional create-if-absent or CAS against the exact authoritative manifest version read for this operation. Never use an unconditional overwrite.

The `prepared` state means no manifest request was dispatched; after a crash, the serialized successor may resolve it as non-committed once it confirms the prior run has ended. A dispatched write is first durably marked `submitting` and remains there until its outcome is durably resolved; a crash in that state requires reconciliation, not an assumption that the request did or did not commit. A response is confirmed committed, confirmed not committed, or unknown. Treat a conditional rejection as confirmed not committed only when tested storage semantics guarantee non-commit. A timeout, connection loss, lost response, or any response that does not guarantee non-commit is unknown. Reconcile a rejected or unknown outcome by reading the manifest through an uncached authoritative path: the exact intended `manifest_write_id` and full intended content prove commit; the exact expected prior version (or confirmed absence for an expected-absent initial create) proves non-commit only when tested store consistency semantics establish that result. Do not infer non-commit merely because a read returns an old state unless those semantics have been verified. A different version, inconclusive read, or unavailable/non-authoritative read proves neither outcome.

After an outcome is known, conditionally update the authoritative journal entry to a terminal `resolved_committed` or `resolved_noncommitted` state before any next manifest mutation or cleanup. The terminal update must itself be confirmed durable; if its response is lost or ambiguous, reconcile the journal update and stop until its state is known. Retain a compact terminal marker for every resolved `manifest_write_id` so later runs cannot replay it; never reuse an ID or remove a resolution marker during artifact cleanup. Keep full intended content for every prepared entry. Any journal read/update whose durability cannot be established is a fail-closed condition.

Every later serialized run, including daily build, scope release, rollback, and cleanup, must read the authoritative journal first and resolve all nonterminal `prepared` or `submitting` entries in order before downloads or other publication-affecting work; cleanup must not delete anything before this recovery step completes. Missing, malformed, or unavailable journal state is not an empty journal unless an explicit authoritative absence is established under tested semantics. If an outstanding outcome or its terminal journal update remains unknown, alert independently and stop: do not retry the manifest write, start a later operation, download inputs, restore/rollback, write an error status, or delete objects. After a durably resolved non-commit, rebuild from the latest authoritative manifest and recheck applicable scope approval/revision and all preconditions before any new write; never reuse a stale candidate. Resolved entries are recorded history, not work to replay. Keep the existing distinction between manifest-based publication and immutable-object accessibility. An uploaded content-addressed object can be publicly fetchable by someone who knows its URL while remaining an unreferenced orphan. A combined catalog is published only when an authoritative `latest.json` manifest points to it. Thus a confirmed rejected first create with confirmed manifest absence means no published catalog, not necessarily no publicly addressable combined object; an unknown create outcome must be reconciled before claiming either state.

### 3. Automate builds without operating a server

- Use GitHub Actions for the daily scheduled workflow and explicit scope-release workflow/action in a public `bls_index` repository on a standard Linux runner. Daily execution is scheduled and also supports manual rebuild dispatch; scope changes require the distinct, explicitly invoked release mode/action with an approved exact target list and confirmation. Put scheduled, manual daily rebuild, scope release, rollback, and cleanup operations that can mutate publication state in the same concurrency group (`group: bls-index-publish`, `cancel-in-progress: false`): a running job is not canceled, but GitHub Actions may replace an older pending request with a newer pending request, so not every trigger is guaranteed to run. This coalescing/replacement is permitted. Operators can see canceled pending runs in GitHub Actions; if a manual action is replaced and its work is still needed, trigger it again. Only runs that actually start execution are attempts; a request canceled before starting must not be recorded as a failed attempt or update per-program attempt/status records. Manual daily rebuilds and release actions run through GitHub Actions, not local machines, so they share the lock. Test actual memory, disk, runtime, BLS network access, and dependency setup. Measure daily Actions minutes, data transfer, and total usage against the applicable GitHub usage caps; configure usage monitoring/alerts and adjust the run only if needed to remain within caps. The research's few-minute full rebuild is an estimate, not a promise. Cloudflare Workers Cron is not the bulk build environment.
- Each started daily run reads and independently downloads, rebuilds, and validates only the programs in published `required_programs` (or the fixed initial 33 if there is no manifest), regardless of whether BLS headers or identifiers appear unchanged. Proposed future programs are not built as part of daily runs. Upload successful compact per-program files to immutable R2 keys and read them back to verify checksums. Before first publication, any failed initial program blocks publication even if an old file exists; record the failure in the GitHub Actions run and alert maintainers independently. Publish the first combined artifact and `latest.json` only after all initial programs succeed in that same run and the combined candidate passes validation. After publication, select last-good files for failed programs in current published scope, assemble and validate the current-scope candidate, calculate its SHA-256 and size, and produce a machine-readable validation summary. On a valid candidate, upload and verify immutable data objects, then atomically write `latest.json` with new `current`, its exact unchanged published program list, and `previous` equal to the complete prior `current` record with a new grace expiry and its real scope-verification timestamp. Update attempt records and overall freshness state for every started daily run where the manifest is writable, calculating complete verification and freshness solely for the published scope. A request canceled before starting is not a failed attempt and must not update those records.
- Before starting any download, the scope-release action validates the operator-supplied `target_programs` list as nonempty, unique, canonical, and supported by implemented and tested builds; compares its exact additions and removals with the current published list; and requires explicit operator confirmation of those exact changes, including any contraction, bound to the approved base-scope fingerprint (`scope_revision` plus exact canonical current `required_programs`). Before downloads, re-read the manifest and compare that fingerprint; immediately before the atomic manifest switch, re-read and compare it again. If either comparison differs, abort without switching scope, request fresh approval, and log/report the stale approval (and alert independently as appropriate); daily artifact or status changes with the same fingerprint do not invalidate approval. Reject empty, duplicate, unknown, noncanonical, unsupported, unconfirmed, or unintended contraction requests before downloading. The approval policy is mandatory, but no particular approval mechanism is prescribed. Only then rebuild every target program from fresh source inputs, with no last-good fallback for any target, including programs already in published scope. It validates the full combined target candidate. Only when every target program succeeds in that run and the candidate passes validation does it upload/read-back-verify immutable objects and atomically write `latest.json` to switch both `current` and `required_programs`, snapshotting the complete prior `current` as `previous`. That successful write advances `last_complete_successful_source_verification_at` for the resulting target scope and pins every target's last-good reference to its corresponding newly validated immutable file, source-built time, and checksum, discarding last-good records outside target; subsequent daily failure for a target uses this release file. A failed release never advances complete verification. It never adds or removes programs automatically based on milestone lists, source contents, missing files, or successful daily builds. On release failure, keep the published artifact pointer and `required_programs` unchanged; log and alert independently. A failure only among programs outside published scope must leave published status unchanged. If a currently published program fails during release, update its attempt/error report and mark the published scope degraded (stale retains precedence) wherever the manifest can be written; do not advance complete verification. Before first publication, release/initial failures are reported in the workflow and independent alert because no manifest is available. No failed scope release may update the artifact record or target scope.
- Alert maintainers on program/build/publication failures and on stale or overdue status. Manifest publication failure is a separate alert condition: attempt an independent notification through the workflow/monitoring path, because the manifest cannot report its own failed write. If status cannot be published, clients detect the old `manifest_updated_at` as overdue. The artifact pointer remains on the last valid catalog when no valid replacement can be assembled or validated.
- Keep source and catalog ages visible. The 48-hour overall stale threshold allows a missed daily run but does not imply that a partially rebuilt catalog is fresh. Frozen datasets are downloaded and rechecked every daily run like live ones. Document upstream outage behavior and the per-program fallback policy.

### 4. Serve safely and cheaply

- Store the Parquet files and manifest in an R2 **Standard** bucket exposed through a dedicated Cloudflare custom domain; turn off the public `r2.dev` URL so security/cache rules cannot be bypassed through it. No API keys for read access; downloads must work from non-browser tools such as R and `curl` without JavaScript challenges. Serve every public object under a versioned path prefix (`/v1/`), so a later host change alters only the hostname and a future incompatible schema can be published beside it. The data host is replaceable and is not the public entry point (see the discovery pointer below); it is provisionally a subdomain of `benzipperer.org`, whose DNS is already on Cloudflare. The bucket must be in the same Cloudflare account as that zone.
- Publish a stable discovery pointer at `https://economic.github.io/bls_index/endpoint.json`, served by GitHub Pages from this public repository (`Economic/bls_index`). It is a small JSON document with an integer `schema_version` (currently 1) and an absolute `https` `manifest_url`, for example `{"schema_version": 1, "manifest_url": "https://<data host>/v1/latest.json"}`. Deploy only a dedicated `pages/` folder, never `docs/` or other repository content. Change `endpoint.json` only through a reviewed commit on a protected `main` (for example with a CODEOWNERS entry); build, release, rollback, and cleanup workflows never write repository contents and do not hold `contents: write`. The manifest URL must use `https`. Publish the production `endpoint.json` only after the first public `latest.json` exists, so the pointer never leads to a missing or staging manifest. Terminology: the catalog is *published* when `latest.json` commits, as defined by the manifest write outcome protocol, and *available to clients* only once the pointer resolves to that manifest. Deploying the production pointer and resolving it from an external machine is therefore a launch condition: alert on and retry a failed Pages deployment, and do not announce the catalog until the pointer resolves. Staging uses a separately named pointer (for example `endpoint.staging.json`) that clients never read by default. Do not rename or move the repository: project Pages URLs follow its name.
- Keep the manifest operation journals (production and staging) and private test data in buckets with no public access. Staging delivery artifacts, meaning the staging manifest and Parquet files that the staging gate downloads without credentials, go in a separate public staging bucket with its own staging hostname. R2 public access is believed to be a bucket-level setting (a custom domain exposes every object in the bucket); verify this, and unless a narrower control is confirmed, keep the private journal in a separate bucket from public artifacts.
- Changing the data host is an operator procedure, not a client release. Because manifest references are relative, the simplest move attaches a new custom domain to the same bucket: objects, manifest, `previous`, last-good records, and the journal stay in place, and nothing is rewritten. If the bucket itself must move (for example to another Cloudflare account), cut over in order under the publication lock: resolve every nonterminal journal entry; copy `latest.json`, every object referenced by `current`, unexpired `previous`, and last-good records, and a snapshot of the journal with all its terminal markers; verify every checksum and the manifest in the new buckets; point all publication workflows at the new buckets; then make the old buckets read-only by revoking their write credentials. From then on the new journal is the only authority. In either case, verify the manifest and every referenced object through the new host, update `endpoint.json` through a reviewed commit, and keep the old hostname redirecting to the new one (for example with a Cloudflare redirect rule) for as long as the old domain is held. There is no relocation notice inside the manifest: clients reach the new host through the redirect, or by refreshing the pointer when the cached manifest URL fails.
- Configure a narrow Cache Rule for immutable `.parquet` paths (not all site traffic), with a long TTL; configure a short TTL for `latest.json` so publication and status changes propagate promptly. Check `Cache-Control`, `ETag`, `Content-Length`, and actual cache hit/miss behavior after launch. `.parquet` is not cached by Cloudflare by default. Avoid cookies or arbitrary query strings in published URLs that fragment the cache.
- Add a conservative per-IP, path-scoped WAF rate-limit **block** rule only after measuring legitimate traffic; leave room for shared institutional IPs. Do not use CAPTCHA/Managed Challenge for the machine-readable download. Add usage and budget alerts, understanding that alerts are not hard cost caps. Document that caching and rate limiting mitigate abuse but do not guarantee a maximum bill. Revisit protections using measured R2 Class B reads and edge hit rates.
- Verify cold download, repeated download, checksum validation, manifest refresh after complete and partial daily runs, scope release, rollback, and old-file cleanup from an external machine. Test both fresh and cached requests and a failure/rollback path. Keep the catalog within the chosen CDN's cacheable size limit or revise serving strategy.

## Interface reserved for future `epidatatools` integration

Publish `data-dict.yaml`, schema and manifest examples, a checksum verification example, a small fixture, and the stable discovery pointer URL. The future client can check the manifest at a documented interval, fetch a new file once to `tools::R_user_dir("epidatatools", "cache")`, verify the checksum and supported catalog schema version, check essential columns/types, swap the cache atomically, and search locally/offline afterward. It does not need the `data-dict` CLI or a full-row validation scan at runtime. Expose catalog source and age to callers, and treat the catalog as stale when the manifest says stale or its update timestamp is over 48 hours old. Consumers must not interpret `degraded` as fresh just because the manifest itself was recently updated. This integration, its user-consent/download UX, API compatibility, CRAN checks, and relevance ranking are **out of scope for this repository**; do not make the index build depend on `epidatatools`.

The client contract nevertheless fixes how a client discovers the catalog and how often it may ask. The client starts from the discovery pointer but contacts it rarely:

- Ship the pointer's current manifest URL in the package as a built-in default. Cache the last good pointer on disk with a long time-to-live (days, not minutes), and refresh it only after that expires or when the cached manifest URL fails (connection error or 404), which is how a host move appears.
- Normally fetch the pointer and the manifest at most once per R session. Revalidate both with `If-None-Match`, since GitHub Pages and R2 return ETags; the ban on conditional requests applies only to the BLS ingest. Recovery may exceed that limit only within fixed bounds: bounded retries of a failed request, and one pointer refresh per session after the manifest URL fails.
- On HTTP 429, 5xx, or an unreachable host, fall back to the cached pointer or the built-in default. Respect `Retry-After` and retry a bounded number of times with backoff, never in a tight loop.
- Accept only `https` manifest URLs. Treat a pointer that is malformed, has an unsupported `schema_version`, or names a non-`https` URL as unavailable: warn and use the cached pointer or the built-in default. Resolve the manifest's relative object paths against the final manifest URL after any redirect. Let users override the manifest URL with a package option or environment variable.
- Send a User-Agent naming `epidatatools` and its version. Download each immutable Parquet file at most once, cached by checksum.

These rules keep bursty use (CI matrices, loops, parallel workers) within GitHub Pages' published limits (a soft limit of 100 GB per month, with possible HTTP 429 rate limiting) and within R2 read budgets.

## Decisions

- **Daily rebuild exactly the published scope; validate independently.** Do not skip work based on `HEAD`, `ETag`, or `Last-Modified`. Every scheduled or manual daily rebuild that starts reads `required_programs` from `latest.json` and downloads/rebuilds each listed program. Before first publication, use only the fixed initial 33-program scope. Repository milestone lists and BLS directory contents never extend daily scope. A pending request canceled before starting is not an attempt and does not update per-program attempt/status records.
- **Require explicit serialized scope releases.** Before any download, validate a nonempty, unique, canonical list of supported target codes, compare the exact additions and removals with current published scope, and require the operator's explicit confirmation of those changes, including contractions, bound to the approved base-scope fingerprint (`scope_revision` plus the exact canonical current `required_programs` list). Increment `scope_revision` only when a successful scope release changes the list; daily artifact and status writes do not change it. Re-read and compare the fingerprint before downloads and immediately before the atomic manifest switch; if it changed, abort without switching scope and request fresh approval. Daily artifact or status changes with the same fingerprint do not invalidate approval. Reject unknown, duplicate, empty, unsupported, unconfirmed, or unintended contraction requests. The approval policy is mandatory, but no particular mechanism is prescribed. Rebuild and validate every confirmed target in the same run with no fallback, validate the full combined candidate, then atomically publish the artifact, exact `required_programs`, complete-verification time for that resulting scope, and target-pinned last-good file/time/checksum records; discard last-good records outside target. A later daily failure uses the release file. A release failure leaves artifact and scope unchanged and never advances verification; a proposed-only failure does not change published status and is logged/alerted independently. If validation fails for any currently published program included in the release attempt, report it against current scope and, where the manifest is writable, set status to degraded unless stale takes precedence. A 404, empty, malformed, or otherwise failed source is never interpreted as a removal request. Contraction/removal has no automatic criteria: the operator explicitly approves the exact remaining target list.
- **Use per-program last-good files for daily rebuilds, never for a scope release.** Each program is an independent validation unit. The first public catalog requires all 33 initial programs to succeed in the same run; do not use older last-good files to make that initial publication. After the first publication, a failed currently published program may use its durable last-good file in a partial daily publication; if it has no valid copy, retain the previous combined artifact. Any successful daily publication keeps the same published scope. A scope release has no fallback: first reject invalid target lists and require explicit confirmation of the exact additions/removals against current scope, bound to the approved base-scope fingerprint (`scope_revision` plus exact canonical current `required_programs`), before downloads; recheck the fingerprint before downloads and immediately before the atomic manifest switch, aborting without a scope switch and requesting fresh approval if it changed; then every exact target program must succeed and validate in the same run, and the full target combined candidate must pass. On success, atomically advance complete verification for target and pin each target last-good record to its newly validated file, time, and checksum, dropping out-of-target records. A bad or absent source never implicitly removes a published program.
- **Publish immutable files before switching the manifest and snapshot rollback state.** For first publication, verify successful same-run files for all 33 initial programs and the assembled combined file, then publish the combined artifact and write `latest.json` last. For every later artifact or scope switch, the same atomic manifest write updates `current` and `required_programs` and sets `previous` to the full prior `current`, including its combined URL/checksum, exact per-program file URLs/checksums, actual source-built times, and actual last-complete-verification timestamp, with a documented grace expiry. Cleanup rereads the manifest under the serialization lock and protects `current`, unexpired `previous`, and current-scope last-good records; expiry removes rollback protection but does not itself delete data. Ordinary rollback verifies all checksums and is permitted only when the previous scope exactly matches the current scope. It atomically swaps exact records, restores actual timestamps, and renews the grace period for the displaced current. In the same write, reset/pin each restored program's last-good reference and time to its exact file and actual source-built time in restored `current`; until that program successfully rebuilds and validates a new file, never use a displaced-version file as its fallback. Keep last-good records only for restored scope; `previous` protects its references during the grace period. Rollback does not count as source verification: mark the restored catalog degraded until a new complete successful daily rebuild of its published scope, with stale taking precedence if its real verification time is older than 48 hours. Do not retain a prior fresh status or assign a new verification time during rollback. A different-scope rollback is not an ordinary rollback; use an explicitly approved scope release to change scope. If the manifest write fails, alert independently and rely on its overdue timestamp for client detection.
- **Distinguish complete verification, mixed freshness, and stale status.** Calculate last-complete-verification time and freshness solely for the published required scope; programs outside published scope neither block nor advance it. Only an artifact made from every program in its resulting published required scope validated in the same daily run or successful scope-release run without fallback, with the corresponding complete-verification time advanced atomically, within 48 hours, may be called fresh. Any fallback for a published program makes it degraded. More than 48 hours since the last complete successful source verification for the published scope makes the catalog stale, taking precedence over degraded. An overdue manifest is also stale to clients. Keep actual per-program source-built timestamps and attempt outcomes visible; do not let a recent successful subset overwrite the timestamp for the last complete run. A proposed-only scope-release failure does not change the published status. If a failed release attempt fails validation for any currently published program included in the attempt, the current scope's status must be degraded unless stale takes precedence, where the manifest is writable; only a successful release advances complete verification for its resulting scope. Rollback restores the artifact's real timestamps but marks it degraded until a new complete successful daily rebuild of that restored scope; it neither preserves a prior fresh status nor fakes a new verification time.
- **Do not require title uniqueness; finish the native-title checkpoint before synthesis.** Native BLS titles may duplicate, so enforce series/lookup correctness rather than unique title strings. Validate the 30 native-title programs first, then implement synthesized titles for the three live untitled initial programs.
- **Keep series liveness out of v1.** The catalog describes which series are present in the current BLS source; it does not decide whether a series is active. `end_year` and `end_period` are not liveness signals. Freshness describes source verification and publication health, not series liveness.
- **Serialize publication operations and keep durable data in R2.** Daily scheduled and manual rebuilds, scope releases, rollbacks, and cleanup use the same GitHub Actions concurrency group with `cancel-in-progress: false`: a running job continues, while a newer pending request may replace an older pending request. This coalescing is permitted; not every trigger is promised to run. Operators can see canceled pending runs in GitHub Actions; if a manual action is replaced and its work is still needed, trigger it again. Only runs that start count as attempts; canceled-before-start requests are not failed attempts. Measure actual usage against GitHub caps. GitHub Actions artifacts are not durable; R2 holds last-good program files, public combined files, and rollback inputs.
- **Discover the catalog through a stable GitHub Pages pointer; treat the data host as replaceable.** Clients start from `https://economic.github.io/bls_index/endpoint.json`, which names the current manifest URL. The EPI GitHub organization is more durable than any domain available now, while R2 still provides conditional manifest writes, immutable objects, and cache control. GitHub Pages cannot do either job alone: it has no conditional writes, a 1 GB site limit, and no HTTP redirects. Only reviewed commits change the pointer; workflows never do. Public objects live under `/v1/`, and the manifest references them by paths relative to its own URL, so a host move usually just attaches a new domain to the same bucket and needs neither a manifest rewrite, a client release, nor a design change. Host moves rely on the pointer, a redirect from the old hostname, and client pointer refresh; the manifest carries no relocation notice, which would need a write to the old host after cutover.
